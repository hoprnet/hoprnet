Runtime state of the SurbBalancer.

§target_surb_buffer_size: AtomicU64§max_surbs_per_sec: AtomicU64§decay_duration_msec: AtomicU64§decay_volume_pct: AtomicU8§buffer_level: AtomicU64§invalid_surbs: AtomicU64

SURBs counted in buffer_level, held in the counterparty’s store, whose return path runs through a relayer judged dead on any hop, and their share of what is outstanding: count in the high and share (of u32::MAX) in the low 32 bits, so both are read together.

§counterparty_buffer_capacity: AtomicU64

How many SURBs the counterparty can physically hold, or 0 when unknown.

The level estimate is produced - consumed - evicted. The Exit observes its own store’s evictions first-hand (num_evicted_surbs on each incoming packet) and counts them, so the level it reports tracks what the store actually holds instead of growing without bound when a return path drops replies – consumption alone is observed only once a reply arrives, and before evictions were counted the belief ran away (measured during an outage: 51 917 believed against a 15 000-entry store).

This capacity still bounds the level, as defense-in-depth, via the max(capacity, target) clamp below: it covers the paths that cannot see evictions – the Entry’s own produced - consumed belief between the Exit’s reports, and any session whose capacity is unknown. The bound is max(capacity, target) rather than capacity so a target above the counterparty’s real store does not pin the error permanently negative and hold production at maximum forever.

§When the store is smaller than the target

With an accurate level, a counterparty whose store is smaller than the target reports a level that plateaus at its real capacity and never reaches target, which on its own would leave organic production running and the full buffer evicting. That corner is closed by observed_counterparty_capacity, which infers the real capacity from the plateau and caps the effective target there. It is unreachable with homogeneous configuration (target <= 2/3 of the store) in any case; it needs the Entry’s store to exceed ~1.5x the Exit’s.

§counterparty_in_surb_distress: AtomicBool

Whether the counterparty’s last packet said it was running low on SURBs of its own.

A plain flag with no deadline: a distress flag that is never withdrawn merely keeps organic production at one SURB per packet — the behaviour that predates the gate — so it does not need to expire.

It clears on its own in the normal case: the counterparty recomputes both SURB signals on every return packet and strips them once its pool recovers, so the next healthy packet resets this.

§observed_counterparty_capacity: AtomicU64

The counterparty’s real store capacity, inferred from where its reported level plateaus, or 0 when not yet inferred.

Closes the capacity < target corner noted on counterparty_buffer_capacity: when the reported level stops rising while the Entry is still minting toward the target and the counterparty is not in distress, its store is full at a level below the target, and that level is its real capacity. organic_surbs_per_packet then stops production at min(target, this) instead of a target the store can never reach.

Biased hard against firing, since a false positive under-supplies the counterparty (see the destructive-recovery note in the SURB balancer gotchas): it takes several consecutive non-rising reports (see observe_reported_level), and a SurbDistress signal discards it outright – a counterparty short of SURBs is not full. Set back to 0 (re-probe) if the level later rises above it.

§capacity_plateau_count: AtomicU64

Consecutive reported levels that did not rise while below target – the plateau hysteresis behind observed_counterparty_capacity.

§counterparty_wiped: AtomicBool

Set by on_counterparty_wiped, consumed by the next balancer update: the counterparty dropped its whole stock, so that update restarts the level estimate from empty.

A flag rather than a plain store of 0 into buffer_level because the level has another writer: the update in flight, which would write back the level it loaded before the reset. (The counterparty’s keep-alive is the other, which may still carry its pre-wipe level; observe_reported_level drops such a report while the refill is paced.)

§refill_pacing: AtomicU64

Paces the refill after a wipe: the rate in SURBs per second in the high 32 bits and the milliseconds it still holds for in the low 32 bits, so both are read together. Zero is inactive. See REFILL_PACING_SECS.

§produced_before_lag: AtomicU64

This side’s produced count as it was REPORT_LAG before the last balancer update, published by every update from ProducedHistory: what a counterparty report arriving now cannot have seen yet is the production since then. 0 until the first update.

§produced_at_update: AtomicU64

This side’s produced count at the last balancer update, published with produced_before_lag. What is produced after it is the next update’s to add, so a report adopted in between takes as in flight only the production up to it.

§correction_cap: AtomicBool

Set when a report lowered the believed level, consumed by the next balancer update: that update’s output is held to the pacing rate, so that a correction never turns into a burst.

§epoch: ActivityEpoch

The instant last_heard and last_sent count from.

§last_heard: AtomicU64

When the counterparty was last heard from, in milliseconds since epoch plus one, so that 0 is “never”. Any packet from it counts, and so does a reply the estimator counted as consumed. Entry-side only; see silence_sustain.

§last_sent: AtomicU64

When a Session data packet last went out, in the same unit as last_heard.

§sending_since: AtomicU64

When the current run of unanswered data began, in the same unit as last_heard: the first packet sent after the counterparty was last heard. See silence_sustain.

§last_reply_heard: AtomicU64

When a reply the estimator counted as consumed last came home, in the same unit as last_heard: what tells a reply stream that stopped from one that never was.

§pacing_floor: AtomicU64

The fewest SURBs per second the paced fill and refill may be held to: one keep-alive’s worth, set by the Session that owns the balancer. 0 until set. See pacing_cap.

§counterparty_refills: AtomicBool

Exit-side: whether the Entry has shown that it refills this side’s SURB stock. See counterparty_refills.

Declares how many SURBs the counterparty’s store can hold, bounding the level estimate.

Taken from the session manager’s maximum_surb_buffer_size, which is the same capacity already used to clamp a counterparty’s requested target. Zero leaves the estimate unbounded.

fn clamp_to_counterparty_capacity(&self, level: u64) -> u64

Caps level at what the counterparty can actually hold.

Never below the configured target: a target above the counterparty’s capacity is unreachable by construction, and clamping to capacity there would hold the error permanently negative and pin production at maximum forever – a worse failure than the unbounded estimate this exists to prevent. In that configuration the capacity figure is simply not usable for this session.

pub fn observe_counterparty_signals(&self, signals: PacketSignals)

Records what the counterparty’s latest packet said about its own SURB supply.

Takes the whole signal set rather than a bool so the containment rule lives here: OutOfSurbs is a superset of SurbDistress on the wire, so contains catches both, whereas an equality match against SurbDistress would silently ignore the more severe of the two.

Source

pub fn observe_reported_level(&self, new_level: u64)

Records the SURB level the counterparty reported, net of the production it cannot have seen yet, and infers its real store capacity from a plateau in that level.

Called on every BalancerState keep-alive, including one that repeats the last value – a level that stops rising while the Entry is still minting toward the target is the plateau signal. See observed_counterparty_capacity.

The report was written REPORT_LAG or less ago, so the SURBs produced since then were still on their way when it was written and are added to it: adopting a report as it stands pulls the level below the truth by exactly that production. Only the production up to the last balancer update is added here, though: the next update adds everything produced after that one to the level in any case, and adding it here as well would count it twice. A report that still lowers the believed level marks the next balancer update so that its output is held to the pacing rate: a correction, not a deficit to burst for.

While the refill after a wipe is paced, every report is dropped, stored by neither the level nor the plateau bookkeeping: a report above the believed level is the counterparty reporting the stock it had before it saw the new SURB generation, and one below it is the stock it had before the refill in flight reached it, thousands short at the pacing rate. The level believed here during the window is the production since the reset, which is the truth by construction.

pub(crate) fn pacing_cap(&self) -> u64

The rate the fill and the refill after a wipe are held to: target / REFILL_PACING_SECS SURBs per second, at least one keep-alive’s worth (set_pacing_floor) and at least one, and never above max_surbs_per_sec.

The floor matters at small targets only: a keep-alive carries a fixed number of SURBs, so a fifth of a target of 11 is two SURBs a second, a keep-alive every four seconds, and a Session that waited for a quarter of its target opened after four seconds instead of under one. The ceiling is the bound the PID output had: the pacing replaces that output for its window, and must not exceed what the client configured the balancer to mint.

Source

pub fn set_pacing_floor(&self, surbs_per_sec: u64)

Sets the fewest SURBs per second the pacing may be held to: one keep-alive’s worth of SURBs, so that a paced fill sends at least one keep-alive a second. See pacing_cap.

Source

pub fn organic_surbs_per_packet(&self) -> usize

How many SURBs an outgoing Session data packet should carry along with its payload.

Entry-side only. BalancerStateValues is shared by both ends of a Session, but only the initiator mints SURBs for its counterparty, so on the Exit this answer is meaningless.

Returning 0 is the point: a SURB delivered to a counterparty that is already at its target evicts the oldest one it holds, and under PIX that destroys an SSA share rather than merely wasting a SURB. Production resumes at one per packet as soon as the estimate falls back below target, or immediately if the counterparty signals it is running low.

This uses the usable level: SURBs the counterparty holds through a relayer judged dead do not hold the gate shut.

pub(crate) fn silence_sustain(&self) -> bool

Whether data is going out into silence: the balancer is enabled, the counterparty was heard from at least once, and data has been going out for more than SILENCE_SUSTAIN_AFTER since the first packet sent after the last time it was. The window starts at that first unanswered packet, not at the last word heard: an idle stretch leaves nothing unanswered, and the Exit gets the grace to answer the data that ends it.

The Entry then keeps one SURB in each data packet it sends even though its level estimate is at or above the target (see cap_organic_surbs in the session manager). The estimate is fed by the Exit’s reports and replies; with none arriving it stays where it was, while the Exit goes on answering the data it gets, one SURB for each reply, into a return path that may be delivering nothing. The estimate then never falls below the target and the Entry mints nothing, until the Exit’s stock is empty. The balancer’s own surb_decay is the exception: on by default (5 % of the target per 60 s) it erodes the estimate each window, so at a data rate low enough that the sustain’s one-SURB-per-packet production does not outpace it, the estimate falls below the target within a decay window or two and the gate reopens without the sustain. One SURB per data packet is what the Exit can be expected to spend and no more: the sustain is bounded by the rate of the data, makes no burst, and wipes nothing. It ends at the first packet or reply from the Exit.

Only a reply stream that stopped counts: the last reply must be within REPLY_STREAM_WINDOW of the last time the counterparty was heard at all. A Session the Exit does not answer hears only its reports, one per notify period, and sustaining it would put one SURB in every data packet into a stock nothing spends, up to the store’s capacity.

Judged between the stamps, not against the clock, so that the answer is about the packet being sent: it takes note_sent for that packet first.

Source

pub fn on_counterparty_wiped(&self)

Tells the state that the counterparty dropped every SURB it held, because the SURB generation of the session advanced and the counterparty clears its store on the first batch of the new one.

The level estimate restarts from empty at the next balancer update, and for REFILL_PACING_SECS the refill is held to the pacing rate: a fifth of the target a second, at least one keep-alive’s worth and never above max_surbs_per_sec (see pacing_cap). The counterparty’s own reports follow suit once the first SURBs of the new generation reach it. Until then it may still report the level it had before, and then the level before the refill in flight reached it; for the paced window every report is dropped (see observe_reported_level).

Source

pub fn arm_refill_pacing(&self)

Holds the refill of an empty counterparty to the pacing rate (pacing_cap: a fifth of the target a second, at least one keep-alive’s worth, never above max_surbs_per_sec) for REFILL_PACING_SECS, whatever the PID would command. A disabled balancer arms nothing.

The second half of on_counterparty_wiped, and what the Entry calls when its balancer starts: a session that has just been opened is in the same state as one that has just been wiped, the counterparty holds nothing and the level estimate says so, and the PID would command its ceiling just the same. Unlike a wipe it resets nothing: the estimate is already empty, and what the first tick produced is the new session’s.
