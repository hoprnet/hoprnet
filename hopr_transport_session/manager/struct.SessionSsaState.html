Expand description

The PIX dimensions this Session negotiated, on the Exit side.

Once carried the SSA index and a fault counter as well. Both moved to the supervisor: it decides when a cycle is requested, so it is also what allocates the index, and it is what enforces the fault limit. Leaving a second copy of either here would have meant two authorities for one fact.

Fields§

§params: PixParams

The dimensions this Session negotiated, as they went on the wire.

§committed_ssa_watermark: AtomicU32

Highest SSA index this Session has had the generator commit to, 0 before the first batch.

A deliberate second copy of a fact the generator already holds, and the only one of the three that came back. The generator’s own watermark lives in a cache with an idle retention, so “absent” there conflates never committed with state discarded — and those must not be treated alike, because the first is the opening batch every Session begins with and the second is a Session whose Entry can no longer serve the cycles it already committed to. This copy lives exactly as long as the Session does, so it can tell them apart. See the successor gate in SessionManager::handle_ssa_request.

Entry-side only; an Exit never commits and leaves it at zero. SsaIndex is a NonZero<u32>, which is what makes 0 an unambiguous “none” rather than a sentinel that has to be defended.

§returned_at_first_commit: AtomicU64

SessionSlot::returned_packets as it stood when this Session first committed.

The successor gate counts service since that instant, not since the Session opened. Before the first commitment the generator holds no polynomials, so the SURBs going out carry no shares — and an Exit may legitimately be served up to max_predeposit_packets of them before any deposit exists. Crediting that prefix would let the Exit bank unpaid service against the first cycle it is paid for. Everything after this point rides a share.

§last_committed_first: AtomicU32

Lowest SSA index of the request this Session most recently committed to, 0 before the first.

What lets the Entry tell a repeat of a request it already served from a stale one. Both ask for an index at or below committed_ssa_watermark; only a repeat names the batch that was last committed. The Exit re-sends an unanswered successor request until it hears back, so a repeat is the ordinary case once a request is admitted and the first burst is still on its way, and answering it with a second commitment would fund the same cycle twice.

Stored once phase two has staged the whole request rather than after the burst is published. A burst that fails to send has still moved the generator, so its re-sends must read as repeats — read as stale instead, each of them would be logged as a fault. Not stored any earlier, though: a batch that fails during phase two after moving the generator can never be committed, and that failure closes the Session rather than leaving its re-sends to be told apart. And a repeat is not always a no-op: while unpublished still holds members of that batch, the repeat is the Exit’s prompt to finish publishing them, and once it has been published a repeat that comes too late to have crossed the bursts is the prompt to send them again.

§unpublished: Mutex<OwedPublications>

Members of the batch last staged whose commitment burst and ReadyToDeposit have not both gone out, with exactly the announcement that is still owed for each.

Phase three sends a member’s whole burst and only then announces its deposit address, and the transport can fail between any two messages (it gives up on a send after EXTERNAL_SEND_TIMEOUT). Without this record the generator has moved on and the failure is final: the Exit’s re-sends read as repeats of a batch the Entry believes it served, and a scoped re-request completes the commitment it names without ever announcing the deposit, so the Exit holds a complete commitment for a cycle nobody was told to fund.

Filled at the end of phase two for every staged member, before anything is sent. A member is published by whoever removes it from here, under this mutex, and by nobody else: phase three claims each member just before its burst, and the resumption that finishes an interrupted batch (resume_publication) claims the same way. Whoever holds the claim announces the deposit once its whole burst is out, so the announcement happens at most once per member however many resumers there are — which matters, because the scoped re-request path does not take the per-pseudonym request lock. A claimant that fails puts its member back, and a member that was never claimed was never touched.

A newer batch replaces whatever is left of an older one: the Exit asks for a successor only after the commitment and the deposit of its predecessor, so an older member still here has been given up on. That, and the batch size the Entry accepts, bound the map. A claimant of an older batch that fails after it was replaced finds its member not wanted back (see OwedPublications).

What this recovers, and what it does not. Only the Exit can prompt a resumption: by a repeat of the request, or by a scoped re-request that names an owed cycle. The Exit re-requests the parts of a commitment that has started to arrive and gone quiet, so a member cut part-way through its burst is finished by the re-request wherever its batch stands — and that resumption publishes every member still owed, not only the one named. A member with no message of it out has nothing to re-request, and only a repeat can reach it. The Exit repeats a successor batch, whole, for as long as any member of it has reported nothing, but only while the batch is behind the front: a batch at the front is never re-sent (the opening batch is at the front from the start, and a successor admitted just before the front moved joins it). So, per member, nothing prompts a resumption in two cases, and a third is given up on:

  • a member with no message of it out whose batch holds the front: the opening batch always, or any member after a cut that lands exactly on a member boundary there, when no earlier member of the batch is itself still owed (its own burst cut part-way), whose re-request would resume it too. The member times out on its commitment deadline;
  • a burst that went out whole whose ReadyToDeposit could not be queued because the PIX event channel was full. The Exit then holds a complete commitment and never asks again. The member is kept owed, in case something does;
  • a cycle whose retransmissions are spent, which can never be published again. It is dropped from here with one warning (see resume_publication).

A member that has been published is out of the owed set, but publishing only means the local transport took the burst. If a relayer on the forward path dies, the whole burst can still be lost. The Exit then has no part it could re-request, so only a repeat reaches the member. A repeat that arrives more than SSA_REPEAT_RESEND_GRACE after the batch last went out has the whole burst of every announced member sent again, and nothing announced (see OwedPublications::announced). The limits are the same as for a resumption: a batch at the front is never repeated, so a lost opening burst is not recovered, and each re-send spends one of the cycle’s retransmissions.

None of these strands a deposit, because nothing was announced for the member concerned: the Exit’s own deadline ends the cycle. The opposite hazard exists, though. A resumed burst answers a re-request, and the Exit’s re-request timer asks until just before the cycle’s commitment deadline without moving it, so the resumption — or a repeat delayed on the way — can arrive after the Exit has retired the cycle. A re-send is a second source of the same thing: re-sends go on up to the deadline of a member that has reported a part, which the tick does not push, so the last one — sent up to one interval before the Exit retires that member — can resume and announce it afterwards. The Entry then announces a deposit for an address nobody can reconstruct.

§last_refusal: AtomicU64

The refusal this Session last logged, as (lowest index asked for, SsaRefusal), 0 for none.

Only to keep the log honest. The Exit re-sends a refused request every few seconds, so the same refusal repeats for as long as the gate stays shut, and a line per re-send would bury the one that matters: the first.

§sent_deposit_data: Arc<Mutex<HashMap<SsaIndex, HoprPixDepositPayload>>>

What this Exit sent as deposit data, per SSA index, for cycles whose deposit address it has not learned yet.

pub fn note_committed(&self, index: SsaIndex, returned_packets: u64)

Raises the committed-index watermark to index if it is higher, taking the returned-packet baseline on the first commitment.

fetch_max rather than a store: the gate serialises requests per pseudonym, but a Session’s slot is shared and monotonicity here must not depend on that lock staying where it is. Its previous value is also what makes the baseline race-free without leaning on that lock — exactly one caller can observe a prior watermark of zero, so exactly one stores.

Hands back a claimed member whose publication did not complete, so that it is owed again.

pub fn complete_publication(&self, claim: ClaimedPublication, now: Instant)

Spends a claim whose publication completed at now: the member’s whole burst is out and its ReadyToDeposit queued.

Recorded only while the claim’s batch is the current one. A newer batch has replaced it otherwise, and the Exit no longer repeats the request this member belonged to.

Source

pub fn claim_republication( &self, now: Instant, grace: Duration, ) -> Vec<SsaIndex> ⓘ

The announced members whose bursts a repeat arriving at now should have sent again, or nothing if the batch last went out less than grace ago.

When it returns members, the batch counts as sent at now. The repeats that follow therefore wait out a whole grace again, and so do the ones that were already on their way. Whether the re-send then gets out does not matter: one that fails is retried no sooner than one that succeeded, which keeps a congested transport from being handed a burst on every repeat.

pub fn forget_announced(&self, index: SsaIndex)

Stops counting index as announced once the generator will not rebuild its burst, so later repeats do not ask for it again.

pub fn note_refusal(&self, first: Option<SsaIndex>, refusal: SsaRefusal) -> bool

Records a refusal, returning whether it differs from the one recorded before it.

pub fn served_since_first_commit(&self, returned_packets: u64) -> u64

Exit → Entry packets received since this Session’s first commitment.

Saturating rather than wrapping: returned_packets is monotonic and the baseline is a past value of it, so an underflow is impossible — and if one ever became possible, reporting zero service closes the successor gate rather than opening it.

pub const fn quota_per_ssa(&self) -> u64

Data quota one SSA cycle of these dimensions covers.

The whole cycle, surplus included, as per pix_params_to_quota: every share a cycle emits rides one Exit → Entry packet, so all of them are priced.
