fn remove_slot_if(

    id: &SessionId,

Expand description

Removes the slot under id if pred accepts it, atomically with respect to any other compute on the same key.

Built on the cache’s compute rather than remove, which does not serialise with a concurrent compute: a plain remove could take out a successor allocated an instant after the check.

Parks the slot’s PIX ledger inside that compute, before the slot is removed. A reconnect under the same pseudonym that no longer finds the slot therefore always finds the ledger in the retention cache; one that still finds the slot reads the ledger from it, and its claim takes the parked copy (the same ledger) out. Parking later, in release_session_slot, left a window between the two in which the reconnect found neither and started a fresh ledger against a generator that still remembered.

The one removal that does not go through here is the cache’s own eviction, which parks in release_session_slot from the eviction listener. A client cannot learn of such a close before that park: the Session’s channel closes when the slot is dropped and its tasks are aborted, both after it. A reconnect that comes regardless (after an outage that let the slot idle out) does not miss it either: SessionManager::new_session first runs the cache’s pending tasks, which evict an expired slot and run the listener synchronously, before it looks the slot up. Only a slot whose idle time runs out within that call’s own few microseconds escapes this.
