Expand description

Minimum number of shares needed to recover one polynomial of an SSA.

32, down from the 128 this was before the split was first re-tuned and the 64 it was after — see below for why it now sits under the measured optimum. Dropping the non-constant coefficient commitments (see SsaPartCommitment) put every commitment-side cost — wire volume, ingest, reconstructor memory, share verification — on polys alone. What still grows with the threshold is Exit interpolation (O(threshold²) per polynomial), fault-detection latency (threshold return packets) and, on the Entry, the per-packet SsaShareGenerator::next_share, which evaluates a threshold-wide polynomial by Horner for every share it emits. The full cost model is documented on DEFAULT_PIX_POLYS_PER_SSA in hopr-transport-session.

§What 64 optimised, and why 32 is deployed instead

Exit reconstruction capacity, deliberately, and not total network CPU. The two sides do not deserve equal weight: an Exit is a shared resource serving 10–30 concurrent clients while each Entry generates only its own shares, so the Exit is the side that saturates first and the one whose per-share cost sets what the network can carry. Both were measured (48 cores, acknowledge_shares/interpolation and SsaShareGenerator::next_share, µs/share):

The Exit curve falls and then flattens: fitting µs/polynomial = A + B·t + C·t² gives A ≈ 81 µs, B ≈ 7.61, C ≈ 0.028, so per share it is A/t + B + C·t — the fixed per-polynomial commitment opening is amortised over threshold shares and punishes low thresholds harder than interpolation punishes high ones. The Exit-only optimum is t = √(A/C) ≈ 54, flat within 0.5 % from 48 to 64, and 64 — the value deployed before the current split — sits within 0.4 % of it.

Under the total column 48 is about 3 % cheaper. That reading is recorded rather than acted on: it weights one Entry’s share generation equally with the Exit work of the 10–30 clients that Exit serves, which is not where the capacity limit is.

The deployed value is 32, below the Exit-only optimum of ~54, and that is a deliberate trade. This table prices one share, but the quota prices polys × (threshold + surplus), and the surplus is a ratio of the threshold that grows as the threshold falls. A configuration that tolerates 50 % share loss therefore needs a lower threshold to be cheap: at polys = 4096, t = 32, s = 79 is 629.6 MiB per cycle where t = 64, s = 126 is 1078 MiB. The Exit pays ~5 % more per share at 32 than at 54, and the Entry pays ~40 % less quota per cycle — which is the side that pays in money rather than in CPU. See DEFAULT_SURPLUS_SHARES for the loss tolerance that fixes the surplus, and note that s/(t+s) is what the tolerance depends on, not s alone.
