74/// Minimum number of shares needed to recover one polynomial of an SSA.
75///
76/// 32, down from the 128 this was before the split was first re-tuned and the 64 it was after —
77/// see below for why it now sits under the measured optimum. Dropping the non-constant
78/// coefficient commitments (see [`SsaPartCommitment`]) put every commitment-side cost — wire
79/// volume, ingest, reconstructor memory, share verification — on `polys` alone. What still grows
80/// with the threshold is Exit interpolation (`O(threshold²)` per polynomial), fault-detection
81/// latency (`threshold` return packets) and, on the Entry, the per-packet
82/// [`SsaShareGenerator::next_share`], which evaluates a `threshold`-wide polynomial by Horner for
83/// every share it emits. The full cost model is documented on `DEFAULT_PIX_POLYS_PER_SSA` in
84/// `hopr-transport-session`.
85///
86/// # What 64 optimised, and why 32 is deployed instead
87///
88/// **Exit reconstruction capacity, deliberately, and not total network CPU.** The two sides do not
89/// deserve equal weight: an Exit is a shared resource serving 10–30 concurrent clients while each
90/// Entry generates only its own shares, so the Exit is the side that saturates first and the one
91/// whose per-share cost sets what the network can carry. Both were measured (48 cores,
92/// `acknowledge_shares/interpolation` and `SsaShareGenerator::next_share`, µs/share):
93///
94/// | threshold | Exit  | Entry | total |
95/// | --------- | ----- | ----- | ----- |
96/// | 16        | 13.15 | 0.90  | 14.05 |
97/// | 32        | 11.12 | 1.20  | 12.32 |
98/// | 48        | 10.62 | 1.51  | 12.13 |
99/// | 64        | 10.68 | 1.82  | 12.50 |
100///
101/// The Exit curve *falls* and then flattens: fitting µs/polynomial = `A + B·t + C·t²` gives
102/// `A ≈ 81 µs`, `B ≈ 7.61`, `C ≈ 0.028`, so per share it is `A/t + B + C·t` — the fixed
103/// per-polynomial commitment opening is amortised over `threshold` shares and punishes *low*
104/// thresholds harder than interpolation punishes high ones. The Exit-only optimum is
105/// `t = √(A/C) ≈ 54`, flat within 0.5 % from 48 to 64, and 64 — the value deployed before the
106/// current split — sits within 0.4 % of it.
107///
108/// Under the total column 48 is about 3 % cheaper. That reading is recorded rather than acted on:
109/// it weights one Entry's share generation equally with the Exit work of the 10–30 clients that
110/// Exit serves, which is not where the capacity limit is.
111///
112/// **The deployed value is 32, below the Exit-only optimum of ~54, and that is a deliberate
113/// trade.** This table prices one *share*, but the quota prices `polys × (threshold + surplus)`, and
114/// the surplus is a ratio of the threshold that grows as the threshold falls. A configuration that
115/// tolerates 50 % share loss therefore needs a *lower* threshold to be cheap: at `polys = 4096`,
116/// `t = 32, s = 79` is 629.6 MiB per cycle where `t = 64, s = 126` is 1078 MiB. The Exit pays ~5 %
117/// more per share at 32 than at 54, and the Entry pays ~40 % less quota per cycle — which is the
118/// side that pays in money rather than in CPU. See [`DEFAULT_SURPLUS_SHARES`] for the loss tolerance
119/// that fixes the surplus, and note that `s/(t+s)` is what the tolerance depends on, not `s` alone.
120pub const DEFAULT_POLY_THRESHOLD: u8 = 32;

122/// Fraction of cycles [`default_surplus_for`] sizes the surplus to carry through the loss of half of
123/// all shares.
124///
125/// The surplus is insurance against *lost* shares — a share is lost when the first relayer of its
126/// return path never acknowledges it, so a dead return relayer takes its whole share of the path's
127/// traffic with it. Half is the design point because it is what losing one of two return relayers
128/// costs, and a cycle that survives it at this rate is one the operator does not have to tune.
129///
130/// [`tolerated_share_loss`] reads the same target in the other direction — the loss a given surplus
131/// carries rather than the surplus a given loss needs — so that the two agree on what "tolerates"
132/// means.
133const SURPLUS_TARGET_CYCLE_RECOVERY: f64 = 0.99;
134
135/// Shares to emit per polynomial beyond `threshold`, to absorb losses: the fewest with which a
136/// cycle of `polys` polynomials still recovers at 99 % when every share is lost independently with
137/// probability one half.
138///
139/// A polynomial reconstructs from the first `threshold` of the `threshold + surplus` shares emitted
140/// for it, so it survives with probability `P(Binom(threshold + surplus, 1/2) >= threshold)`. A
141/// *cycle* recovers only if **every** one of its `polys` polynomials does — the SSA is the sum of
142/// their constant terms — so that probability is raised to the power `polys`, and the surplus
143/// depends on the polynomial count as well as on the threshold.
144///
145/// This replaced a fixed ratio, `threshold / 4`, documented as covering 20 % share loss. It covered
146/// 20 % per *polynomial*; with the exponent applied, a cycle of 4096 tolerated about 3 %, and the
147/// former `8192 × (64 + 16)` about 5 %. Deriving from the target also gives every split the same
148/// tolerance, where any fixed ratio gives each a different one.
149///
150/// The required ratio *falls* as the threshold rises — at 4096 polynomials it is 52 surplus shares
151/// at threshold 16 (3.3×), 79 at 32 (2.5×), 126 at 64 (2.0×) and 211 at 128 (1.6×) — because a
152/// larger sample concentrates around its mean.
153///
154/// **Saturates at 255**, the byte the surplus travels in. From a threshold of around 160 the target
155/// needs more than that, and the result is then the most the wire can carry rather than a surplus
156/// meeting the target.
157///
158/// `const` so that [`DEFAULT_SURPLUS_SHARES`] can be defined by it, and deterministic for the same
159/// reason: it is evaluated with IEEE `f64` addition, multiplication and division only, whose results
160/// are fixed.
161pub const fn default_surplus_for(polys: u16, threshold: u8) -> u8 {
162    let mut surplus = 0u8;
163    while surplus < u8::MAX
164        && cycle_recovery_at_half_share_loss(polys, threshold, surplus) < SURPLUS_TARGET_CYCLE_RECOVERY
165    {
166        surplus += 1;
167    }
168    surplus
169}

171/// Probability that a cycle of `polys` polynomials, each emitting `threshold + surplus` shares,
172/// recovers when every share is lost independently with probability one half.
173const fn cycle_recovery_at_half_share_loss(polys: u16, threshold: u8, surplus: u8) -> f64 {
174    let emitted = threshold as u32 + surplus as u32;
175
176    // The per-polynomial failure tail `P(Binom(emitted, 1/2) < threshold)`, summed term by term
177    // rather than taken as one minus the success: the tail is ~1e-6 at the deployed split, and the
178    // subtraction would cancel most of its digits. `C(emitted, 0) / 2^emitted` underflows nothing,
179    // since `emitted` is at most 510.
180    let mut term = 1.0f64;
181    let mut i = 0;
182    while i < emitted {
183        term *= 0.5;
184        i += 1;
185    }
186    let mut failure = 0.0f64;
187    let mut k = 0u32;
188    while k < threshold as u32 {
189        failure += term;
190        term = term * (emitted - k) as f64 / (k + 1) as f64;
191        k += 1;
192    }
193
194    // `(1 - failure)^polys` by squaring, since `powi` is not `const`.
195    let mut base = 1.0 - failure;
196    let mut exponent = polys;
197    let mut recovery = 1.0f64;
198    while exponent > 0 {
199        if exponent & 1 == 1 {
200            recovery *= base;
201        }
202        base *= base;
203        exponent >>= 1;
204    }
205    recovery
206}

208/// The largest per-share loss rate at which a cycle of `polys` polynomials, each emitting
209/// `threshold + surplus` shares, still recovers at 99 % — the target [`default_surplus_for`] sizes
210/// the surplus to, so the deployed split tolerates just over the 50 % it was derived for.
211///
212/// Shares are taken to be lost independently. A polynomial survives with probability
213/// `P(Binom(threshold + surplus, 1 − loss) >= threshold)`, the cycle with that raised to the power
214/// `polys`, and the result falls monotonically as the loss rises; the rate where it crosses the target
215/// is found by bisection, to within 2⁻⁶⁰.
216///
217/// **Not `surplus/(threshold + surplus)`.** That is the break-even ratio: the loss at which a
218/// polynomial receives exactly `threshold` shares *on average*. Around half of all polynomials fall
219/// short of their average, and a cycle needs every one of them, so a cycle at break-even fails. At
220/// the deployed `4096 × (32 + 79)` the ratio is 71.2 % and this is 50.3 %; a cycle losing 71.2 % of its
221/// shares recovers with probability indistinguishable from zero.
222///
223/// Evaluated in log space, which is what lets one implementation serve the whole accepted range. The
224/// recurrence [`default_surplus_for`] uses starts from the all-lost term `loss^(threshold + surplus)`
225/// and multiplies its way up from there; at 510 shares that term underflows to zero for any loss
226/// below about a quarter and takes every later term with it, while the tolerances the bisection has
227/// to reach in that corner run down to 10⁻⁹. Here each term is a logarithm, the tail is a
228/// log-sum-exp, and the cycle probability is `exp(polys · ln(1 − tail))` rather than a power of
229/// `1 − tail`, whose subtraction keeps only ten or so of the tail's digits at the deployed split.
230///
231/// Not `const`, because `ln` and `exp` are not, and nothing needs it to be: this prices service
232/// at runtime rather than defining a constant.
233///
234/// A cycle with no polynomials, or polynomials with a zero threshold, recovers whatever is lost, and
235/// tolerates a loss of one.
236pub fn tolerated_share_loss(polys: u16, threshold: u8, surplus: u8) -> f64 {
237    // Each step halves the bracket, so 60 of them leave it at 2⁻⁶⁰ — absolute, and still under a
238    // relative 10⁻⁹ at the smallest tolerance in the accepted range, ~2.4 × 10⁻⁹.
239    const BISECTION_STEPS: u32 = 60;
240
241    if cycle_recovery_at_share_loss(polys, threshold, surplus, 1.0) >= SURPLUS_TARGET_CYCLE_RECOVERY {
242        return 1.0;
243    }
244
245    // Recovery is one at no loss and below the target at total loss, so the crossing lies between.
246    let (mut tolerated, mut fatal) = (0.0f64, 1.0f64);
247    for _ in 0..BISECTION_STEPS {
248        let loss = 0.5 * (tolerated + fatal);
249        if cycle_recovery_at_share_loss(polys, threshold, surplus, loss) >= SURPLUS_TARGET_CYCLE_RECOVERY {
250            tolerated = loss;
251        } else {
252            fatal = loss;
253        }
254    }
255    tolerated
256}

258/// Probability that a cycle of `polys` polynomials, each emitting `threshold + surplus` shares,
259/// recovers when every share is lost independently with probability `loss`.
260///
261/// The general form of [`cycle_recovery_at_half_share_loss`], in log space — see
262/// [`tolerated_share_loss`] for why.
263fn cycle_recovery_at_share_loss(polys: u16, threshold: u8, surplus: u8, loss: f64) -> f64 {
264    if polys == 0 || threshold == 0 || loss <= 0.0 {
265        return 1.0;
266    }
267    if loss >= 1.0 {
268        return 0.0;
269    }
270
271    let emitted = threshold as u32 + surplus as u32;
272    let ln_delivered = (-loss).ln_1p();
273    let ln_lost = loss.ln();
274
275    // `ln` of the terms of the per-polynomial failure tail, `C(emitted, k) (1 − loss)^k
276    // loss^(emitted − k)` for `k < threshold`, with the binomial coefficient built up alongside.
277    // Recomputed rather than collected, so that the two passes of the log-sum-exp allocate nothing.
278    let ln_terms = move || {
279        let mut ln_choose = 0.0f64;
280        (0..threshold as u32).map(move |k| {
281            let ln_term = ln_choose + k as f64 * ln_delivered + (emitted - k) as f64 * ln_lost;
282            ln_choose += ((emitted - k) as f64).ln() - ((k + 1) as f64).ln();
283            ln_term
284        })
285    };
286    let peak = ln_terms().fold(f64::NEG_INFINITY, f64::max);
287    let ln_failure = peak + ln_terms().map(|ln_term| (ln_term - peak).exp()).sum::<f64>().ln();
288
289    // Clamped because rounding can carry a tail of one a hair past it, and `ln_1p` of anything below
290    // minus one is NaN rather than the zero recovery it means.
291    let failure = ln_failure.exp().min(1.0);
292    (polys as f64 * (-failure).ln_1p()).exp()
293}

319/// Retransmission requests the Entry answers for one SSA cycle.
320///
321/// A cycle's commitment ships as hundreds of packets, and a single lost one strands the whole cycle
322/// (see [`SsaShareGenerator::recommit`]), so the Exit must be able to ask again for the pieces it
323/// never received. This bounds how often it may: one request can legally name every polynomial of
324/// the cycle, and an answer is the entire burst again, so an unbounded count is a packet
325/// amplification lever available to a peer that has already been served.
326///
327/// Eight, because the Exit re-asks on an idle timer rather than once. At the shipped Exit settings
328/// — a 3 s re-request interval inside a 20 s commitment deadline — a cycle can produce about six
329/// attempts, and a peer batching several SSAs per request produces proportionally more against a
330/// scaled deadline. The excess is simply refused: an unanswered request costs the Exit one packet
331/// and this node nothing, which is why the two sides are not required to agree on the figure.
332pub const MAX_COMMITMENT_RETRANSMISSIONS: u8 = 8;

334/// Cycles per pseudonym whose commitment material the [`SsaShareGenerator`] retains for
335/// retransmission.
336///
337/// The newest this many are kept and the oldest is evicted, and within a live cache entry that is
338/// the only thing that releases them — emission deliberately does not enter into it. (The entry as a
339/// whole goes on idle eviction, which is a separate lifetime; see below.) Whether a re-sent commitment is
340/// still worth anything is a question about what the peer holds, and none of that is visible from
341/// this side: it completes a cycle out of the shares it has already buffered plus the commitment it
342/// is still missing, on its own delivery deadline. Releasing on drain instead would give up the
343/// repair exactly where it is worth most, a cycle whose every share has gone out and whose only
344/// missing piece is the one a lost packet took.
345///
346/// Eighteen is `MAX_OVERLAPPING_BATCHES` (2) generations of `MAX_SSA_BATCH_SIZE` (9) cycles, the
347/// figures `hopr-transport-session` is built to; they are not visible from here, so the derivation is
348/// written down rather than imported. It leaves a cycle covered for the whole of its own batch plus
349/// one further generation, and the successor gate makes that second generation expensive — a peer
350/// cannot reach it without draining nearly every cycle of the first, by which point it has been
351/// asking for far longer than [`MAX_COMMITMENT_RETRANSMISSIONS`] attempts on any sane re-request
352/// interval allow.
353///
354/// Costs `polynomials_per_ssa × 33 B` per cycle — 135 kB at the deployed dimensions, 2.4 MB per
355/// pseudonym with the cap full. Entry-side state, which is why it is not charged against an Exit's
356/// incoming-Session memory budget: that reserves reconstructor state for Sessions this node *serves*,
357/// and nothing else the generator holds is charged there either.
358///
359/// It lives as long as the pseudonym's entry in the generator's cache, which idle eviction alone
360/// releases — closing a Session clears nothing here. So a node holds this for every pseudonym it has
361/// committed a cycle for within that window, Sessions long closed included, and churn accumulates it
362/// rather than it tracking the live Session count.
363/// What bounds the consequence is that the same entry keeps its polynomial state under exactly the
364/// same rule, and that term is larger by a factor of about sixty: 135 kB here against ~8 MB there,
365/// per cycle. A Session whose cycles are still queued when it closes — the ordinary case, since
366/// draining one takes `polynomials_per_ssa × (threshold + surplus)` shares, 455 k at the deployed
367/// dimensions — leaves both, and this is under 2% of it. Reaching the cap instead means having
368/// drained eighteen cycles, some eight million shares, by which point the polynomials are gone and
369/// 2.4 MB is the entire residue.
370///
371/// Clearing the entry outright at Session teardown would release both sooner, and is worth doing for
372/// the polynomial term; [`SsaShareGenerator::forget`] exists for it, but no production path calls it
373/// today.
374pub const MAX_RETAINED_COMMITMENT_CYCLES: usize = 18;

389/// Protocol-wide floor on [`SsaReconstructorConfig::early_recovery_threshold`].
390///
391/// The Entry refuses a successor `SsaRequest` that arrives before the current batch can plausibly
392/// have been recovered — see [`min_emission_for_early_recovery`]. That boundary is a function of the
393/// *Exit's* `early_recovery_threshold`, and the two sides negotiate [`PixParams`] but not this: it is
394/// a local reconstructor setting on the Exit, and the Entry computing the gate has no way to read it.
395///
396/// So the Entry computes the gate at this floor instead of at its own value, and every Exit is
397/// required to sit at or above it. That turns an unshared value into a shared one without a wire
398/// change, and it is sound in the only direction that matters — an Exit at or above the floor asks at
399/// or after the point the Entry admits, so no conforming pair can fail to communicate. Deriving the
400/// gate from the Entry's own setting instead left two individually valid configurations that could
401/// not talk: an Exit configured lower sent its one-shot request early, the Entry silently dropped it,
402/// and the Session died waiting for a commitment that was deliberately refused.
403///
404/// Equal to the shipped default today, but a separate constant on purpose. The default is a policy
405/// choice an operator may raise; this is a compatibility bound, and *lowering* it is a protocol
406/// break — every Entry still running the old value would refuse the earlier request. Raising it is
407/// equally breaking in the other direction, since Exits at the old floor become unservable.
408///
409/// Enforced where the two halves meet rather than in [`SsaReconstructorConfig`]'s own validator: a
410/// reconstructor exercised on its own has no peer to be incompatible with, and pinning the
411/// early-recovery logic in a unit test needs thresholds well below anything deployable.
412pub const MIN_EARLY_RECOVERY_THRESHOLD: f64 = 0.85;
413
414// The shipped default must itself be admissible under the floor it is checked against. The two are
415// defined independently and only compared at configuration time, so a default lowered below this
416// would ship, validate every hand-written config, and then be rejected the moment an operator wrote
417// the default out explicitly — or worse, be accepted locally and refused by every conforming Entry.
418// Asserted here rather than only in a test because it costs nothing and cannot be skipped.
419const _: () = assert!(
420    SsaReconstructorConfig::DEFAULT_EARLY_RECOVERY_THRESHOLD >= MIN_EARLY_RECOVERY_THRESHOLD,
421    "SsaReconstructorConfig::DEFAULT_EARLY_RECOVERY_THRESHOLD must not sit below MIN_EARLY_RECOVERY_THRESHOLD — a \
422     stock Exit would ask for its next SSA batch before any conforming Entry admits the request"
423);

500    /// Derives the Fiat–Shamir challenge of an [`SsaCommitmentProof`] over the client's
501    /// `ssa_commitment` and the prover's `nonce_commitment`.
502    ///
503    /// `ssa_id` is bound in so that a proof cannot be replayed onto a different SSA index or a
504    /// different Session's pseudonym.
505    ///
506    /// The Exit's own commitment is deliberately **not** bound in. The statement being proven is
507    /// knowledge of `dlog(ssa_commitment)` alone, and the deposit is protected because the Exit's
508    /// secret is what separates that from `dlog(ssa_commitment + exit_commitment)` — which holds
509    /// regardless of what the challenge hashes. Binding it would only prevent reusing one proof for
510    /// the same `ssa_commitment` against two different Exits, and an Entry that reuses its
511    /// commitment does know its discrete log, so that case is honest (reuse is a linkability
512    /// concern, not an exploit).
513    fn commitment_proof_challenge(
514        ssa_id: &SsaId<Self::Pseudonym>,
515        ssa_commitment: &PixGroup<Self>,
516        nonce_commitment: &PixGroup<Self>,
517    ) -> errors::Result<PixScalar<Self>, Self::Pseudonym>
518    where
519        Self: Sized,
520    {
521        let ssa_index = ssa_id.ssa_index().get().to_be_bytes();
522        let ssa_commitment = ssa_commitment.to_bytes();
523        let nonce_commitment = nonce_commitment.to_bytes();
524
525        hash_to_scalar::<Self::Curve, ExpandMsgXmd<Self::Digest>, <Self::Curve as Curve>::FieldBytesSize>(
526            &[
527                ssa_id.pseudonym().as_ref(),
528                ssa_index.as_ref(),
529                ssa_commitment.as_ref(),
530                nonce_commitment.as_ref(),
531            ],
532            &[
533                Self::HASH_TO_SCALAR_SUITE_ID,
534                Self::HASH_COMMITMENT_PROOF_CONTEXT.as_bytes(),
535            ],
536        )
537        .map_err(|_| errors::PixError::InvalidInput)
538    }

575/// Commitment to the constant term of the polynomial with the given [`SsaPolynomialId`].
576///
577/// ## Why only the constant term
578///
579/// This used to be a full Feldman verifier — a commitment to *every* coefficient — so that each
580/// individual share could be checked the moment it arrived. Classic VSS needs that, because its
581/// shares sit with mutually distrusting parties that reconstruct later. PIX has exactly **one**
582/// shareholder: the Exit holds every share, reconstructs locally, is the whole quorum, and
583/// consumes only the recovered constant term. Checking `a₀·G == C₀` once, on the reconstructed
584/// part, is therefore deterministic and exact for the property actually relied upon — and costs
585/// one scalar multiplication per polynomial instead of `threshold` per share.
586///
587/// What the per-coefficient commitments did buy was fault *isolation*: one bad share could be
588/// rejected on arrival and its slot refilled from the surplus. That is given up. A share that
589/// fails to reconstruct implies a dishonest or broken Entry — it travels inside a
590/// Sphinx-authenticated SURB, and its decryption key is fixed by the very acknowledgement
591/// challenge it is filed under, so there is no benign path to a corrupt one — and such an Entry
592/// has already funded the deposit it thereby forfeits. The price paid is detection latency:
593/// a dishonest Entry is caught on the `threshold`-th share of a polynomial rather than the first.
594///
595/// [`surplus_shares`](SsaGeneratorConfig::surplus_shares) still absorbs *lost* shares, since
596/// reconstruction starts at the first `threshold` distinct shares that arrive.
597#[derive(Debug, Clone, PartialEq, Eq)]
598#[cfg_attr(feature = "serde", derive(serde::Serialize, serde::Deserialize))]
599pub struct SsaPartCommitment<S: PixSpec, P = <S as PixSpec>::Pseudonym> {
600    pub(crate) spi: SsaPolynomialId<P>,
601    #[cfg_attr(feature = "serde", serde(with = "elliptic_curve_tools::group"))]
602    pub(crate) constant_term: PixGroup<S>,
603}
604
605impl<S: PixSpec> SsaPartCommitment<S, S::Pseudonym> {
606    /// Creates a commitment from an **already decoded and subgroup-checked** group element.
607    ///
608    /// The only decode is [`decode_commitment`](Self::decode_commitment), performed once when the
609    /// commitment arrives on the wire. Decompression requires a modular square root and is the
610    /// dominant per-commitment cost, so nothing here decodes a second time.
611    #[inline]
612    pub fn from_decoded_commitment(spi: SsaPolynomialId<S::Pseudonym>, constant_term: PixGroup<S>) -> Self {
613        Self { spi, constant_term }
614    }
615
616    /// Returns the [`SsaPolynomialId`] of the polynomial this commitment belongs to.
617    #[inline]
618    pub fn spi(&self) -> &SsaPolynomialId<S::Pseudonym> {
619        &self.spi
620    }
621
622    /// Returns the commitment to the constant term of the polynomial.
623    #[inline]
624    pub fn constant_term(&self) -> &PixGroup<S> {
625        &self.constant_term
626    }
627
628    /// Checks a reconstructed constant term against this commitment.
629    ///
630    /// This is the *entire* verification the Exit performs on a polynomial, and it happens once,
631    /// after `threshold` shares have been interpolated. A mismatch means at least one of those
632    /// shares did not come from the committed polynomial; it does not say which.
633    #[inline]
634    pub fn verify_reconstructed(&self, secret: &PixScalar<S>) -> bool {
635        PixGroup::<S>::mul_by_generator(secret) == self.constant_term
636    }
637
638    /// Decodes a single serialized coefficient commitment into a group element.
639    ///
640    /// Rejects bytes that do not decode, and points outside the prime-order subgroup: Baby JubJub
641    /// has cofactor 8, so small-order points can pass the plain on-curve check.
642    ///
643    /// No value-based filtering is applied — a coefficient commitment equal to the generator
644    /// validly represents scalar coefficient 1 and must be preserved.
645    pub fn decode_commitment(commitment: &PixGroupRepr<S>) -> errors::Result<PixGroup<S>, S::Pseudonym> {
646        Option::<PixGroup<S>>::from(PixGroup::<S>::from_bytes(commitment))
647            .filter(|pt| bool::from(pt.is_torsion_free()))
648            .ok_or(errors::PixError::InvalidInput)
649    }
650}
