1//! PIX supervision for incoming PIX-enabled sessions.
2//!
3//! This module implements the **Exit-side** supervision logic for sessions
4//! using the Protocol for Incentivization of eXits (PIX).  The Exit node
5//! runs a deterministic supervisor that tracks each *Secret Sharing Aggregate*
6//! (SSA) through a well-defined lifecycle, enforcing timeouts, deposit
7//! sufficiency, recovery progress, and fault tolerances.  Egress data
8//! packets are gated behind a concurrent `ServiceGate` that follows the
9//! front cycle: bounded predeposit service while it is unfunded and a
10//! ceiling-limited path after it funds.
11//!
12//! # Why supervision is needed
13//!
14//! PIX sessions use SSAs: cryptographic aggregates that distribute the
15//! cost of a deposit across many packets sent from the Entry to the Exit.
16//! Each SSA requires:
17//!
18//! 1. A **commitment** from the Entry (polynomial coefficients) that the Exit can verify.
19//! 2. A **deposit** to an SSA-specific on-chain address before the Exit fully trusts the SSA.
20//! 3. **Recovery** of the SSA shares from data packets as they arrive.
21//!
22//! Without supervision, a misbehaving or stalled Entry can hold a session
23//! slot indefinitely without ever funding or completing recovery — a
24//! resource-exhaustion vector.  The supervisor enforces hard per-SSA and
25//! per-session bounds so the Exit can reclaim resources deterministically.
26//!
27//! # Architecture
28//!
29//! The module is split into three components:
30//!
31//! | Component | File | Role |
32//! |---|---|---|
33//! | `SessionPixSupervisor` | `supervisor` | Pure state machine — no I/O, no async, no spawning.  Driven by explicit `Instant` timestamps and service-gate snapshots. |
34//! | `ServiceGate` | `gate` | Concurrent, lock-free egress gate.  Before the front funds: bounded predeposit budget.  After it funds: ceiling on packets served without that cycle's recovery progress.  Callers park on a generation-counter waker. |
35//! | Worker loop | `worker` | Per-session actor that bridges the pure supervisor to async reality.  Receives commands via a backpressured channel, manages the deadline timer, applies gate actions synchronously, and forwards actions to the caller. |
36//!
37//! The [`SlotNotify`](crate::utils::SlotNotify) multi-waker primitive is shared from [`utils`] and used
38//! by `ServiceGate` to park and wake callers without a tokio dependency.
39//!
40//! ## The `SessionPixSupervisor` state machine
41//!
42//! The supervisor tracks each SSA through these phases:
43//!
44//! ```text
45//! RequestSsa  ──►  SsaRequestSent  ──►  AwaitingCommitment
46//!                                          │
47//!                                     CommitmentVerified
48//!                                          │
49//!                                      AwaitingDeposit
50//!                                          │
51//!                                     DepositConfirmed (≥ expected)
52//!                                          │
53//!                                        Recovering
54//!                                          ├── (idle re-arms when no service)
55//!                                          ├── hard deadline is immutable
56//!                                          └── progress resets idle timer
57//!                                          │
58//!                                     Recovered
59//!                                          ├── bounded paid FIFO drain
60//!                                          ├── successor progress → handoff
61//!                                          └── diagnostic tombstone expiry → RetireSsa
62//! ```
63//!
64//! **Key deadlines** (all configurable via [`SupervisorConfig`]):
65//!
66//! * **Commitment timeout** — time from `SsaRequestSent` to `CommitmentVerified`.
67//! * **Deposit timeout** — time from `CommitmentVerified` to a sufficient deposit.
68//! * **Recovery idle** — time without *any share arriving* while service is being consumed. **Service-gated**: if no
69//!   packets were served since the last progress snapshot, the timer re-arms instead of closing (prevents a
70//!   slow-but-honest Entry from being disconnected). Deliberately not "useful progress": a conforming Entry emits a
71//!   whole window's surplus in one run, none of it useful, and treating that as silence closes honest Sessions.
72//! * **Recovery hard deadline** — absolute per-SSA backstop, never extended. This is a resource guard (session slot +
73//!   reconstructor memory), not a liveliness mechanism.
74//!
75//! Both recovery clocks start when the cycle reaches the **paid transport front**, not when its
76//! deposit confirms. A batch is served in index order, and the final SURBs buffered for a recovered
77//! predecessor still carry that predecessor's shares. The predecessor keeps its original immutable
78//! hard clock while this bounded tail drains; the successor's clocks start only when the negotiated
79//! remainder is exhausted or funded successor progress proves the FIFO boundary. A queued cycle is
80//! therefore not charged for either its batch wait or its predecessor's pipeline delay.
81//!
82//! **Fault tracking** — an `UnverifiableShares` event closes the Session on arrival, with no
83//! tolerance to configure and no running totals to keep: the event means a polynomial's share set
84//! failed to open its commitment, which permanently dooms the cycle. Late fault reports against an
85//! already terminal SSA are absorbed. Progress is the one narrow exception: the sole immediate
86//! recovered predecessor may report its bounded, already-paid FIFO tail. See the configuration
87//! section below for why this is not a dial.
88//!
89//! **Rolling SSAs** — to maintain continuity, the supervisor requests the *next* batch when the
90//! current one is "almost recovered" (early threshold reached) or fully recovered, so the commitment
91//! and deposit work for the next cycle overlaps the tail of the current one. With a batch, only its
92//! **last** cycle may ask: the request flags are per-cycle, so without that gate every member would
93//! answer its own early signal with a batch of its own, compounding into `ssas_per_request` batches
94//! per batch. The last rather than the first, because a batch is served in index order and gating on
95//! the first would ask a whole batch too early. Retiring the cycle holding the gate hands it to the
96//! newest survivor, or a batch whose last cycle lost its deposit would strand with no successor.
97//!
98//! Allocation independently enforces the reservation: at most
99//! `MAX_OVERLAPPING_BATCHES` generations and
100//! `MAX_OVERLAPPING_BATCHES × ssas_per_request` live cycles may own reconstructor state. If the
101//! early signal arrives while both generations are still live, the supervisor records the owed
102//! request and retries it only after one generation releases its heavyweight cycle state. Recovered
103//! supervisor tombstones do not count because full recovery removes their heavyweight reconstructor
104//! state; one constant-bounded per-Session tail receipt is tracked separately.
105//!
106//! ## The `ServiceGate` — egress gating
107//!
108//! Every egress data packet from the Exit back to the Entry must pass
109//! through the `ServiceGate` via `acquire`:
110//!
111//! ### Pre-funding (predeposit)
112//!
113//! While the current front cycle is unfunded, a provisional budget lets the Exit answer the Entry
114//! for a bounded number of packets, so that the application is not held up for as long as an
115//! on-chain deposit takes to confirm. The initial front starts with this allowance; a successor gets
116//! a fresh allowance after its predecessor was funded and leaves the front, whether by recovery or a
117//! tolerated failure. A failed funded cycle has already cost the Entry its full deposit, and
118//! `max_failed_cycles` bounds how often that can happen. Losing an unfunded front does not mint
119//! another grant. The budget is
120//! `min(target_useful_shares - 1, max_predeposit_packets)`; at production dimensions the first term
121//! is in the hundreds of thousands, so the configured cap is what binds and the `min` only matters
122//! for the small dimensions used in tests.
123//!
124//! When the budget is exhausted, `acquire` parks the caller on a
125//! `SlotNotify` future. A concurrent `release_service`, `withhold_service`,
126//! `notify_progress`, or `poison`
127//! wakes all parkers.
128//!
129//! ### Strict prepay (`max_predeposit_packets = 0`)
130//!
131//! Zero is a supported setting, and it means the Exit serves nothing against any unfunded front:
132//! the first egress data packet parks, and the Entry has to commit and fund that cycle before a
133//! single payload byte flows back to it. The rule is restored on every paid rotation rather than
134//! applying only to the Session's first SSA.
135//!
136//! This does not deadlock, because nothing on the path to funding passes through the gate:
137//!
138//! * The `SsaRequest` goes out on the [`SessionManager`]'s own message sender, not the Session's gated sink.
139//! * The Entry's commitment travels Entry→Exit, and the deposit is on-chain.
140//! * The SURB-level keep-alive stream is deliberately left ungated, precisely so an exhausted budget cannot silence the
141//!   signal that keeps the Session fundable. Under strict prepay this carries more weight than it does at a non-zero
142//!   budget: with no egress at all, the keep-alives are the *only* traffic reaching the Entry, and therefore the only
143//!   thing resetting the idle timer on the Entry's own session slot. An operator who both sets this budget to zero and
144//!   disables `surb_balance_notify_period` gives the Entry nothing to stay alive on, and it will evict the Session
145//!   before a deposit can land.
146//!
147//! So the Entry can always be asked for a deposit and can always answer, whatever the budget is.
148//! What a zero budget costs is latency, not liveness: the application stalls until the deposit
149//! confirms, instead of proceeding optimistically. If the deposit never arrives, the deposit
150//! deadline closes the Session and `poison` fails the parked writer rather
151//! than leaving it pending.
152//!
153//! ### Post-funding (ceiling)
154//!
155//! Once the current front's deposit is confirmed and the supervisor emits `ReleaseService`, the
156//! gate flips to funded mode. It then enforces `max_served_without_progress`: a
157//! ceiling on how many packets may be served between SSA recovery progress
158//! events, as a defense-in-depth backstop even when the supervisor's
159//! service-gated idle timer is alive. Only progress from that funded front—or from its sole bounded
160//! recovered predecessor while the FIFO drains—emits `ProgressNotification` and resets the
161//! watermark; unfunded, off-front, older, or over-budget progress cannot buy service. A rotation to
162//! an unfunded successor emits `WithholdService` and restores the bounded allowance. A funded
163//! successor stays open, but another `ReleaseService` rebaselines its ceiling.
164//!
165//! The gate is implemented with lock-free atomics and CAS loops.  It uses
166//! the generation-counter `SlotNotify` to avoid the two classic
167//! race conditions of waker-vector approaches:
168//!
169//! 1. **Latent wake** — notification between future creation and first `poll()` is caught because the generation was
170//!    captured at creation time and compared on `poll()`.
171//! 2. **Spurious `Ready`** — a second `poll()` of an already-registered future re-checks the generation; if unchanged
172//!    it stays `Pending`.
173//!
174//! ## The Worker — bridging pure logic to async
175//!
176//! `spawn_supervisor_worker` creates the `SessionPixSupervisor`,
177//! the `ServiceGate`, and a bounded async command channel.  It returns
178//! a `SessionPixSupervisorHandle` (cloneable, for sending events) and an
179//! `ActionRx` receiver (for driving actions).
180//!
181//! The worker loop:
182//!
183//! 1. Reads the next deadline from the supervisor.
184//! 2. If the deadline has already expired, calls `handle_deadline` immediately.
185//! 3. Otherwise, waits on the command channel with a timeout set to the remaining deadline duration.
186//! 4. On command received → calls `handle_event` or `action_result`.
187//! 5. On timeout → calls `handle_deadline`.
188//! 6. Applies gate-control actions immediately, then forwards all actions to the action channel (non-blocking
189//!    `try_send`).
190//!
191//! **Coalescing** — `ProgressNotification` actions are coalescible: when
192//! the action channel is transiently full, they are dropped rather than
193//! blocking or failing the worker. The gate has already consumed the notification locally, and the
194//! next forwarded notification replaces it for observers.
195//!
196//! All other actions (`RequestSsa`, `ReleaseService`, `WithholdService`, `RetireSsa`, `Close`)
197//! are non-coalescible — if they cannot be delivered, the channel is
198//! genuinely wedged and the worker fails the session.
199//!
200//! ## Integration with [`SessionManager`]
201//!
202//! ### Exit side (incoming sessions)
203//!
204//! When `handle_incoming_session_initiation` processes a session request
205//! with `Capability::UsePIX`:
206//!
207//! 1. Validates the offered PIX parameters (polys, threshold, quota range).
208//! 2. Spawns the supervisor worker via `spawn_supervisor_worker` (this emits the initial `RequestSsa` action and
209//!    creates the gate).
210//! 3. Reads the initial action, calls `send_ssa_request` on the wire, and notifies the supervisor of `SsaRequestSent`.
211//! 4. Stores the supervisor handle and gate in the session slot (via `OnceLock`).
212//! 5. Constructs the [`HoprSession`] — the egress adapter acquires the gate on every outgoing data packet.
213//! 6. After session publication, spawns the **action driver task** that receives actions from `ActionRx`. Gate control
214//!    has already happened in the worker; the driver performs I/O and records the gate-mode telemetry:
215//!
216//!    | Action | Behaviour |
217//!    |---|---|
218//!    | `RequestSsa` | Calls `send_ssa_request`, feeds back result to supervisor. Tracks each SSA in `SsaCommitmentGuard` for Drop-safe cleanup. |
219//!    | `ReleaseService` | Worker calls `gate.release_service()`; driver records funded telemetry. |
220//!    | `WithholdService` | Worker calls `gate.withhold_service()`; driver records unfunded telemetry. |
221//!    | `ProgressNotification` | Worker calls `gate.notify_progress()`; no driver I/O. |
222//!    | `RetireSsa` | Calls `share_processor.retire_ssa`, aborts the deposit observer task. |
223//!    | `Close` | Poisons gate, retires all SSAs, publishes close metric, removes session slot. |
224//!
225//! 7. PIX protocol events from the packet pipeline arrive via `dispatch_pix_event` and are forwarded to the supervisor
226//!    as `SessionPixEvent::RecoveryProgress`, `UnverifiableShares`, `AlmostRecovered`, or `Recovered`.
227//! 8. When a commitment becomes verifiable, a `PixDepositObserver` task loops on deposit confirmations, forwarding each
228//!    as `DepositConfirmed` to the supervisor.
229//!
230//! ### Entry side (outgoing sessions)
231//!
232//! The Entry does **not** run a supervisor — the Exit is authoritative for
233//! lifecycle decisions.  The Entry creates a session slot when
234//! `new_session()` succeeds, but the slot's `pix_supervisor` and
235//! `pix_egress_gate` remain unpopulated.  On receiving an `SsaRequest`
236//! from the Exit, the Entry generates its client commitment via the
237//! share generator, sends the commitment messages, and emits
238//! `ReadyToDeposit` so the caller can fund the deposit address.
239//!
240//! ## Lifecycle sketch (Exit side)
241//!
242//! ```text
243//! Session Initiation (Entry→Exit, with UsePIX flag)
244//!     │
245//!     ▼
246//! handle_incoming_session_initiation
247//!     │  validate PIX params
248//!     │  spawn supervisor (emits initial RequestSsa)
249//!     │  send SsaRequest on the wire
250//!     │  install gate & handle in slot
251//!     │  construct HoprSession (egress adaptor acquires gate)
252//!     │  spawn action driver
253//!     ▼
254//! ┌────────────────────────────────────────────────────┐
255//! │  Ongoing lifecycle (concurrent)                    │
256//! │                                                    │
257//! │  Entry → CommitmentVerified  → supervisor          │
258//! │  Entry → DepositConfirmed    → supervisor (via     │
259//! │                                PixDepositObserver) │
260//! │  Packets → share_processor   → RecoveryProgress    │
261//! │  Action: ReleaseService       → gate.release_service│
262//! │  Action: WithholdService      → gate.withhold_service│
263//! │  Action: ProgressNotification → gate.notify_progress│
264//! │  Action: RequestSsa (next)   → send on wire        │
265//! │  Action: RetireSsa           → reconstructor.retire│
266//! │  Action: Close               → poison + teardown   │
267//! └────────────────────────────────────────────────────┘
268//! ```

270//! # Configuration
271//!
272//! ## What each parameter prevents
273//!
274//! Every field of [`SupervisorConfig`], the failure it exists to stop, and what shipping default it
275//! carries. Nothing here is a preference: each one is the only thing standing between the Exit and a
276//! specific way of taking service without paying for it.
277//!
278//! | Parameter | Default | What it prevents |
279//! |---|---|---|
280//! | `ssas_per_request` | 1 | Nothing by itself — an exposure dial. With dynamic batching it is the largest batch the Exit may derive; otherwise it is the exact batch size. Raising it amortises the request round trip over several cycles, at the price of multiplying the *unfunded* exposure to that many quotas, and it scales the two deadlines below. |
281//! | `allow_dynamic_ssa_batches` | true | Lets a sub-range per-SSA offer satisfy `quota_range` by committing to the smallest batch whose total quota enters the range. Disable it to retain the fixed-batch, per-SSA admission rule. |
282//! | `max_failed_cycles` | 1 | An Entry losing one cycle per batch indefinitely while a single funded sibling holds the Session open. One loss is survivable, the second closes the Session. Only reachable above a batch of one, where the failing cycle is not always the last one standing. |
283//! | `max_ssa_delivery_time` | 20 s | An Entry that accepts a request and never delivers the commitment set, holding a session slot and a reconstructor cycle that can never be funded. |
284//! | `max_deposit_wait` | 60 s | An Entry that commits but never deposits — typically after it has already drawn the predeposit budget. |
285//! | `max_recovery_idle` | 60 s | An Entry, or a colluding first return relayer, consuming service while returning no shares. Service-gated, so a Session that is merely quiet is never punished. |
286//! | `max_recovery_time` | 2 h | A cycle that dribbles just enough progress to refresh the idle timer forever. A resource backstop for the slot and the reconstructor state, *not* the anti-drip rule. It must clear a whole cycle at the widest dimensions the node accepts — 655 360 packets of *full emission*, ~61 min, at the defaults — or it closes honest Sessions instead. That is the quantity `quota_range` prices and `validate_incoming_session_pix_config` enforces; the *last useful share* lands earlier, at 651 264, which is the figure the "why two hours" argument on [`SupervisorConfig::max_recovery_time`] uses. |
287//! | `max_off_front_share_fraction` | 0.25 | An Entry spreading a batch's shares across all of its cycles, taking `ssas_per_request` quotas of service while completing none of them — and a cycle short of completion pays nothing at all. |
288//! | `min_share_order_sample` | 16384 | Convicting on a thin sample: the shares that legitimately cross a cycle boundary out of order while in flight. |
289//! | `max_predeposit_packets` | 10000 | Bounds what an Entry can extract from an unfunded front. Restored only after a paid front handoff; `0` means strict prepay on every rotation. |
290//! | `max_served_without_progress` | 2048 | Packets served with no share of *any* kind coming back — in *packets*, so unlike the idle timer the bound does not move with the Session's rate. Counts `shares_seen`, so a conforming Entry's surplus resets it; see below. |
291//! | `tombstone_retention_window` | 30 s | Bounds how long recovered-cycle diagnostics and observer ownership remain; the separately bounded FIFO-tail receipt may outlive it. |
292//!
293//! ## What is *not* here: the price of a cycle
294//!
295//! No parameter above says what a quota costs, and none should. The Exit's deposit pool is handed the
296//! [`DepositUpdated`](hopr_api::node::DepositUpdated) sender along with
297//! [`AgreedSsaQuota`] when the deposit address arrives, and it is the component
298//! that knows both the byte quota and the price it charges for one. It sends on that channel once the
299//! deposit clears that price; the supervisor's `DepositConfirmed` handler acts on the verdict rather
300//! than recomputing it. The Entry side mirrors this — its own strategy prices the `quota` carried by
301//! `PixEvent::NewDepositAddress` and decides what to pay.
302//!
303//! There was briefly a `min_deposit` here, and a per-SSA `expected_deposit` on the commitment event to
304//! go with it. Both are gone. The Session layer has no price for a byte to derive one from, and a
305//! configured floor would not be a backstop but a second authority behind the first: set above the
306//! pool's price it kills a cycle the pool has already been paid for, on `max_deposit_wait`, with
307//! nothing on either side able to break the tie.
308//!
309//! ## The one fault with no dial: unverifiable shares
310//!
311//! An `UnverifiableShares` report closes the Session immediately, and there is no configuration for
312//! it. This used to be a pair of tolerances, per-SSA and per-Session, both shipped at zero.
313//!
314//! Shares are not checked on arrival — the non-constant coefficient commitments that made per-share
315//! verification possible were dropped — so a report means a whole *polynomial's* share set failed to
316//! open its commitment. The reconstructor marks that part failed, releases its shares, and never
317//! clears the flag; the SSA is the sum of every polynomial's constant term, so from that moment the
318//! cycle cannot be reconstructed by any means and will never pay. A tolerance would therefore not buy
319//! recovery, only unpaid service — including in the case it looks written for, a false positive from
320//! a verification bug, where the part is just as permanently failed. Closing on the first report also
321//! caps the exposure at the `threshold` packets already served when the failure surfaces, rather than
322//! a multiple of it.
323//!
324//! What the tolerances bought instead was machinery: absolute cross-peer totals, per-SSA and
325//! per-Session running sums, and delta accounting against the maximum seen so far to keep concurrent
326//! ack batches from double-counting. None of it is observable at a limit of zero, since the first
327//! report ends the Session.
328//!
329//! ## Constraints between parameters
330//!
331//! [`validate_pix_supervision`] enforces, at config-load time and against the reconstructor config
332//! actually in use: `max_recovery_idle >= max_ack_await_time`; `tombstone_retention_window >=
333//! max_ack_await_time`; `max_recovery_idle < unused_verifier_lifetime`; `ssas_per_request` in
334//! `1..=MAX_SSA_BATCH_SIZE`; both scaled deadlines under 24 h; non-zero durations; a share fraction in
335//! `0.0..=1.0`; and non-zero `max_served_without_progress`, `min_share_order_sample` and
336//! `max_failed_cycles`.
337//!
338//! ### The surplus run, and why it no longer constrains anything
339//!
340//! Emission is round-robin over a window of up to `hopr_protocol_pix::SHARE_EMISSION_WINDOW` (256)
341//! polynomials advancing in lockstep. They reach `threshold` on the same pass and then take their
342//! surplus shares together, so every block ends with `surplus_shares × window` consecutive packets
343//! carrying no *useful* share — **4096 at the shipped dimensions**, against a
344//! `max_served_without_progress` of 2048.
345//!
346//! That used to be a live constraint on two parameters, and an unmeetable one: the ceiling and the
347//! idle timer both counted useful shares, so the run looked exactly like an Entry gone silent. The
348//! gate would park the writer partway through, a parked writer spends no SURBs, and the idle rule
349//! could not rescue it — its re-arm branch needs *no service consumed* since the last progress, and
350//! 2048 packets were. An honest Session closed with `RecoveryIdle` one emission block into a cycle.
351//!
352//! Both now read [`SsaRecoveryProgress::shares_seen`](hopr_protocol_pix::SsaRecoveryProgress::shares_seen),
353//! which counts every share the cycle accepts — surplus included, up to the negotiated budget per
354//! polynomial. Full cryptographic recovery no longer cuts that signal off: the reconstructor drops
355//! its heavy state but retains one shared per-polynomial remainder, and the supervisor keeps that
356//! recovered predecessor as the paid front until the tail is exhausted or successor progress proves
357//! the FIFO boundary. The run therefore resets the ceiling and refreshes the idle deadline exactly
358//! like the useful shares around it, even across recovery, so **neither parameter has to be sized
359//! against the dimensions any more.** What `max_served_without_progress` still bounds is genuine
360//! silence: packets served with no share of any kind coming back.
361//!
362//! The one dimension-dependent property that remains is not a supervisor parameter at all: a
363//! polynomial's whole emission, `threshold + surplus`, should fit one peer deferral bucket
364//! (`hopr_protocol_pix::MAX_DEFERRED_ACKS_PER_POLYNOMIAL`, 128), or acknowledgements arriving before
365//! the cycle's commitments install can be dropped. The shipped 96 fits; both halves are a byte wide
366//! on the wire, so the sum can reach 510. It is a sufficient condition rather than a required one —
367//! only the pre-install prefix is deferred — which is why it is asserted on the defaults rather than
368//! enforced.
369//!
370//! ## Worked example
371//!
372//! A profile of **5 Mbps sustained per direction** and **5–6 s on-chain settlement** for an SSA
373//! deposit. `HoprPacket::PAYLOAD_SIZE` is 1038 B, so 5 Mbps is ~602 packets/s of return traffic —
374//! one SURB and one share each.
375//!
376//! **Dimensions first**, because every supervisor value derives from them. `2048 × 64` with the
377//! derived surplus of 16 gives 131 072 useful shares out of 163 840 emitted, and a cycle of 163 840
378//! packets — about **4.5 min** at this rate. The quota is priced on all of them, surplus included, so
379//! it is `2048 × 80 × 1038 B` = **162.2 MiB**, which is exactly the bottom of the default
380//! `quota_range` (a quarter of the 648.8 MiB the default dimensions imply), so no range change is
381//! needed. The default `8192 × 64` would make that 18.1 min per cycle, which at 6 s settlement is a
382//! long time to leave one cycle's traffic unsettled for no benefit. Keep it a multiple of 256 so the
383//! emission window never narrows.
384//!
385//! | Parameter | Value | Why, at this profile |
386//! |---|---|---|
387//! | `PixGlobalConfig::num_ssa_parts` (Entry) | 2048 | 162.2 MiB quota, 4.5 min cycle; multiple of the emission window |
388//! | `PixGlobalConfig::ssa_part_size` (Entry) | 64 | Shipped threshold; with the surplus below, it is what fixes the quota |
389//! | `PixGlobalConfig::additional_shares` (Entry) | unset | Derives to 16 — a quarter of the threshold, i.e. a 1.25× surplus factor and a fifth of the quota. Setting it explicitly buys loss tolerance and charges the Entry for it. Keep `ssa_part_size + additional_shares` inside one deferral bucket (128) |
390//! | `ssas_per_request` | **1** | The 85 % early signal leaves a 24 627-packet runway — **41 s** — before the cycle drains, against 6 s of settlement plus a commitment round trip. There is nothing to amortise, and a batch of `n` would multiply the unfunded exposure to `n × 162.2 MiB` |
391//! | `max_ssa_delivery_time` | 20 s | 2048 commitments ship in ~71 forward packets, well under a second; the margin covers commitment generation |
392//! | `max_deposit_wait` | 30 s | 5× the 6 s settlement, leaving room for the Entry to notice `ReadyToDeposit`, submit, and the observer to see it |
393//! | `max_predeposit_packets` | 4096 | ~6.8 s of service, matching expected settlement rather than the deadline. This is the most exposed against an unfunded front after the initial grant or a paid handoff — 4.2 MB. Use `0` for strict prepay at every rotation; normal overlap usually funds the successor before it reaches the front |
394//! | `max_served_without_progress` | 2048 | Shipped value, and no longer dimension-dependent: the surplus run resets it like any other share, so this bounds genuine silence only |
395//! | `max_recovery_idle` | 60 s | Shipped value. Satisfies `>= max_ack_await_time` and `< unused_verifier_lifetime`. It no longer has to cover the surplus run — that resets it — so what it now implies is only that a Session returning *nothing at all* for a minute is closed |
396//! | `max_recovery_time` | 2 h | Resource backstop only. A cycle needs 272 s at full rate, so 2 h implies a floor of ~23 packets/s (~0.19 Mbps) — deliberately far below the idle rule, which is the instrument that should bind |

433/// Configuration for the `SessionPixSupervisor`.
434///
435/// Reachable from a node's configuration file as
436/// `incoming_session_pix_config.supervision`. The fields interact — with each other and with the
437/// reconstructor's own lifetimes — so a set of them is only meaningful as a whole; that is what
438/// [`validate_pix_supervision`] checks, and the node's config validator runs it at load time.
439///
440/// A worked set of values, and what each field defends against, is written out under
441/// "Configuration" in the `supervision` module documentation — the module is crate-private, so it is
442/// named rather than linked here.
443#[derive(Debug, Clone, PartialEq, smart_default::SmartDefault, serde::Serialize, serde::Deserialize)]
444#[serde(default, deny_unknown_fields)]
445pub struct SupervisorConfig {
446    /// Maximum number of SSAs the Exit may ask the Entry to commit to in one `SsaRequest`.
447    ///
448    /// With [`allow_dynamic_ssa_batches`](Self::allow_dynamic_ssa_batches), Session admission picks
449    /// the smallest batch no larger than this value whose total quota is inside the Exit's accepted
450    /// range. With dynamic batching disabled, this remains the exact batch size, preserving the
451    /// original fixed-batch behavior. Batching amortizes the request round trip over several deposit
452    /// cycles. It lives here rather than beside the other Exit settings because the supervisor acts
453    /// on the selected value: it allocates the indices and scales both deadlines below by this factor.
454    ///
455    /// Two things it costs, both linear in the value:
456    ///
457    /// * Up to two batches can own live reconstructor state — worst case ≈41 MiB per cycle at the profiled dimensions,
458    ///   per `hopr_protocol_pix::peak_cycle_bytes`. That cost is reserved up front against
459    ///   `IncomingSessionPixConfig::max_live_cycle_bytes`; the supervisor enforces the two-generation/full-cycle bound
460    ///   before allocating, so this value directly divides the number of PIX Sessions the node will admit.
461    /// * The unfunded exposure within one batch: every cycle is initially requested unfunded, so the commitment and
462    ///   deposit deadlines cover this many SSA quotas rather than one. The front-aware service gate still grants only
463    ///   the current cycle's bounded predeposit allowance.
464    ///
465    /// **Must not exceed the peer Entry's `max_ssas_per_request`.** The batch size is not negotiated
466    /// — `StartSession.additional_data` is fully allocated (PIX dimensions in the upper 32 bits, SURB
467    /// balancer target in the lower 32), so the Entry cannot advertise its cap and the Exit cannot
468    /// learn it. An Entry that finds a batch too large refuses it in full and replies with an
469    /// `UnacceptablePixParams` `SessionError`, which closes the Session on both sides in about a round
470    /// trip. Every such Session is still lost; the reply only makes the failure immediate and
471    /// attributable instead of surfacing as a commitment timeout.
472    ///
473    /// Range-checked by [`validate_pix_supervision`] and clamped where it is read, so it can never
474    /// exceed `MAX_SSA_BATCH_SIZE`.
475    ///
476    /// Default: 1, which reproduces the unbatched exchange byte-for-byte.
477    #[default(1)]
478    pub ssas_per_request: usize,
479
480    /// Whether Session admission may derive a smaller SSA batch from the Entry's offered quota.
481    ///
482    /// When enabled, the Exit tries batch sizes from one through
483    /// [`ssas_per_request`](Self::ssas_per_request) and selects the first whose total quota is inside
484    /// `IncomingSessionPixConfig::quota_range`. If none fits, the Session is refused with
485    /// `UnacceptablePixParams`. Choosing the smallest fit limits Entry work, deposits, Exit memory,
486    /// and the chance of exceeding the Entry's unadvertised `max_ssas_per_request` cap.
487    ///
488    /// When disabled, the offered per-SSA quota itself must be inside `quota_range`, and the Exit
489    /// requests exactly `ssas_per_request` SSAs, matching the behavior before dynamic batching.
490    ///
491    /// Default: `true`.
492    #[default(true)]
493    pub allow_dynamic_ssa_batches: bool,
494
495    /// Cycles this Session may lose without recovering them before it is closed. The next one closes
496    /// it.
497    ///
498    /// Counted over the whole Session, not per batch, because a retired cycle leaves no trace on its
499    /// siblings: without a cumulative count an Entry can lose one cycle per batch forever while a
500    /// single funded sibling keeps the Session alive, paying for a fraction of what it is served.
501    ///
502    /// Only reachable with [`ssas_per_request`](Self::ssas_per_request)` > 1`. At the shipping batch
503    /// of one the failing cycle is always the last one standing, and that closes the Session before
504    /// this is ever consulted — so nothing changes at the defaults.
505    ///
506    /// A recovered cycle never counts: it leaves through tombstone expiry, not through the failure
507    /// path.
508    ///
509    /// Default: 1 — one lost cycle is survivable, which is what the retire-and-hand-on-the-successor
510    /// -gate path exists for, and a second is not.
511    #[default(1)]
512    pub max_failed_cycles: usize,
513
514    /// Maximum time to wait for the SSA to be fully committed.
515    ///
516    /// Together with [`max_deposit_wait`](Self::max_deposit_wait) this bounds how long a Session may
517    /// be served unincentivized: the Entry has to be able to deliver its SSA commitment before it
518    /// can be asked to pay for it.
519    ///
520    /// Multiplied by [`ssas_per_request`](Self::ssas_per_request) when the deadline is armed: a batch
521    /// asks the Entry for that many commitment sets in answer to one request, and all of their clocks
522    /// start together, so holding each to a single cycle's budget would fail an Entry that is
523    /// answering in order.
524    ///
525    /// Default: 20 s.
526    #[default(Duration::from_secs(20))]
527    #[serde(with = "humantime_serde")]
528    pub max_ssa_delivery_time: Duration,
529
530    /// Maximum time to wait for a deposit after the commitment is verifiable.
531    ///
532    /// Also multiplied by [`ssas_per_request`](Self::ssas_per_request). Each cycle's clock starts at
533    /// its own commitment, which staggers them somewhat — but a batch's commitments arrive
534    /// back-to-back while an Entry funding them serially finishes the last one that many deposits
535    /// later, so the stagger does not cover it.
536    ///
537    /// Default: 60 s.
538    #[default(Duration::from_secs(60))]
539    #[serde(with = "humantime_serde")]
540    pub max_deposit_wait: Duration,
541
542    /// Maximum idle time during recovery when service is being consumed.
543    ///
544    /// Gated on service consumption — if no packets were served, the timer
545    /// re-arms instead of closing.
546    ///
547    /// Default: 60 s.
548    #[default(Duration::from_secs(60))]
549    #[serde(with = "humantime_serde")]
550    pub max_recovery_idle: Duration,
551
552    /// Absolute per-SSA recovery deadline (immutable once set).
553    ///
554    /// This is a **resource backstop** (session slot + reconstructor memory),
555    /// not the anti-drip mechanism. The service-gated idle rule is.
556    ///
557    /// ## Why two hours, and not one
558    ///
559    /// It has to cover the *whole* of a cycle at the dimensions the node will accept, and at the
560    /// default dimensions one cycle does not fit in an hour. Emission runs in lockstep over windows
561    /// of [`SHARE_EMISSION_WINDOW`](hopr_protocol_pix::SHARE_EMISSION_WINDOW) polynomials, so with
562    /// 8192 polynomials the last useful share of the cycle lands at
563    ///
564    /// ```text
565    /// (31 full windows x 80 emitted + 1 window x 64 useful) x 256 = 651 264 packets
566    /// ```
567    ///
568    /// which is just over **60 minutes** at the 1.5 Mbps per-Session cap this crate documents, before
569    /// any mixing latency or loss. A one-hour ceiling closes an honest, fully saturated Session at
570    /// the default configuration with its last useful share only about 18 seconds away — and the
571    /// partial cycle is worth nothing, since the SSA is the sum of every polynomial's constant term.
572    ///
573    /// This is deliberately not the same count as the 655 360 quoted in the module documentation's
574    /// parameter table, and the two must not be reconciled: 655 360 is `8192 × 80`, the *full*
575    /// emission including the last window's surplus, which is what `quota_range` prices and what
576    /// `validate_incoming_session_pix_config` checks this value against. 651 264 is where the last
577    /// *useful* share lands, which is the point this argument is about — a deadline that clears the
578    /// useful shares but not the surplus tail still collects a payable cycle.
579    ///
580    /// Two hours is the value the worked profile in the module documentation already used, and it
581    /// keeps this instrument where it belongs: far enough out that
582    /// [`max_recovery_idle`](Self::max_recovery_idle) is what actually binds.
583    ///
584    /// The clock starts when the cycle reaches the paid transport front. That is deliberately later
585    /// than merely becoming the earliest unrecovered record: the predecessor's buffered surplus tail
586    /// can still occupy ~4096 packets, ~23 s at that rate, and remains bounded by the predecessor's
587    /// original hard clock. Starting the successor at the FIFO boundary prevents that pipeline delay
588    /// from being charged twice. A funded cycle that reaches the front and is never served is still
589    /// caught.
590    ///
591    /// `HoprProtocolConfig::validate` checks this against the dimensions the node will actually
592    /// accept, so a raised `quota_range` that outgrows it is refused at load rather than discovered
593    /// one closed Session at a time.
594    ///
595    /// Default: 2 hours.
596    #[default(Duration::from_secs(7200))]
597    #[serde(with = "humantime_serde")]
598    pub max_recovery_time: Duration,
599
600    /// Largest share of recovery progress that may land on a cycle *other* than the one at the front
601    /// of the batch, as a fraction of all progress since that cycle took the front.
602    ///
603    /// ## What it defends
604    ///
605    /// A batch only de-risks the Exit if its cycles are served one at a time, so that recovering the
606    /// first pays for the traffic that earned it. An Entry that instead spread a batch's shares across
607    /// all `ssas_per_request` cycles could take `ssas_per_request × quota` of service while leaving
608    /// every cycle short of recovery — and a cycle short of recovery pays nothing at all, since the SSA
609    /// is the sum of *every* polynomial's constant term. That turns the batch knob from cost-neutral
610    /// into an n-fold amplifier of unpaid traffic.
611    ///
612    /// Nothing else sees it. The service gate and [`max_recovery_idle`](Self::max_recovery_idle) both
613    /// measure the *absence* of progress, and a spreading Entry makes progress on every cycle
614    /// continuously — including the front one, whose idle timer it therefore keeps refreshing. It
615    /// simply never finishes one.
616    ///
617    /// ## Why a fraction and not a count
618    ///
619    /// Out-of-order *arrival* is not an Entry property. SURBs cross the mixnet outbound and their
620    /// acknowledgements cross it again inbound, so arrival order is a permutation of emission order
621    /// whose width is roughly `delay_range × packet rate`. An absolute tolerance would therefore have
622    /// to be re-derived every time the mixer is reconfigured, and — being cumulative — would drift
623    /// into closing honest Sessions given enough cycle boundaries.
624    ///
625    /// A ratio has neither problem: a permutation of bounded width is a vanishing *fraction* of a
626    /// growing window, so widening `delay_range` cannot move it, and the denominator grows with the
627    /// numerator so nothing accumulates. It is also independent of packet **rate** (both terms scale
628    /// together, so unlike a wall-clock bound it implies no throughput floor), of **loss** (which hits
629    /// every cycle alike), and of **`surplus_shares`** — which matters even now that the surplus is
630    /// negotiated rather than Entry-private. The Exit knows the budget, not the spend: how many of a
631    /// cycle's emitted shares turn out to be useful depends on the loss the Entry actually met, so no
632    /// expected shares-per-packet ratio follows from the parameter. Comparing the batch's cycles
633    /// against each other cancels it.
634    ///
635    /// ## The value
636    ///
637    /// A conforming Entry sits at ~0: with emission clamped to one cycle
638    /// ([`hopr_protocol_pix::SHARE_EMISSION_WINDOW`]) the only off-front progress is boundary
639    /// reordering. Spreading across `n` cycles gives `(n − 1) / n` — 0.5 at two cycles, 0.67 at three.
640    /// 0.25 separates those with room on both sides.
641    ///
642    /// It bounds rather than eliminates: an Entry may divert up to this fraction and stay legal, so
643    /// worst-case unpaid exposure becomes ~`1 / (1 − f)` cycles instead of `n`. Alternating — serving
644    /// the front cycle honestly, then dumping on later ones — buys nothing, because the accounting only
645    /// resets when the front cycle *completes*, which means it was paid for.
646    ///
647    /// Default: 0.25.
648    #[default(0.25)]
649    pub max_off_front_share_fraction: f64,
650
651    /// Progress that must accumulate before
652    /// [`max_off_front_share_fraction`](Self::max_off_front_share_fraction) is judged at all, in useful
653    /// shares.
654    ///
655    /// A sample-size floor, not a tolerance: it does not bound how much a cheat can extract — the
656    /// fraction does that — it only refuses to convict on thin evidence.
657    ///
658    /// Sized by the one case that would otherwise produce a false positive: a cycle made
659    /// *unrecoverable* by loss. A polynomial that loses more than `surplus_shares` of its shares can
660    /// never reach its threshold, so its cycle stops progressing while later ones continue, and the
661    /// off-front fraction climbs to 1.0. That cycle is not something to close a Session over — it stops
662    /// progressing, its service-gated [`max_recovery_idle`](Self::max_recovery_idle) deadline expires,
663    /// it is retired, and the accounting resets on the new front. The sample floor only has to outlast
664    /// that window: ~181 shares/s at the deployed 1.5 Mbps cap over 60 s is ~10 900, so 16 384 leaves
665    /// ~1.5x headroom.
666    ///
667    /// Unlike an absolute tolerance this does not have to grow with Session length or track the mixer
668    /// configuration — it is a floor on evidence, evaluated once and then continuously.
669    ///
670    /// Very large values can make this rule effectively inert for a Session. To disable share-order
671    /// enforcement intentionally, prefer
672    /// [`max_off_front_share_fraction = 1.0`](Self::max_off_front_share_fraction). No fixed upper bound
673    /// is enforced because the accounting window can span multiple successor batches before the front
674    /// advances.
675    ///
676    /// Default: 16384 shares.
677    #[default(16384)]
678    pub min_share_order_sample: u64,
679
680    /// Cap on the provisional predeposit service budget.
681    ///
682    /// This buys the application an exchange while the current front cycle's deposit confirms on
683    /// chain; it is not needed for the Session to become fundable, so it is a
684    /// latency-versus-exposure dial rather than a correctness requirement. The initial front starts
685    /// with this allowance, and it is restored for an unfunded successor after a paid front leaves
686    /// the front, whether by recovery or a tolerated failure. Retiring an unfunded front does not
687    /// grant it again.
688    ///
689    /// **Zero is supported and means strict prepay**: the Exit answers nothing until a sufficient
690    /// deposit is confirmed. Everything on the path to funding — the `SsaRequest`, the Entry's
691    /// commitment, the deposit itself, and the SURB keep-alive stream — bypasses the egress gate, so
692    /// a zero budget stalls the application without ever stalling the funding handshake. Deliberately
693    /// *not* rejected by [`validate_pix_supervision`] for that reason, unlike
694    /// [`max_served_without_progress`](Self::max_served_without_progress), where zero would wedge a
695    /// Session that has already paid.
696    ///
697    /// The effective budget is `min(target_useful_shares - 1, max_predeposit_packets)`, so this value
698    /// is the binding one at any realistic set of PIX dimensions.
699    ///
700    /// Default: 10000 packets.
701    #[default(10000)]
702    pub max_predeposit_packets: u64,
703
704    /// Maximum packets served without a single share coming back, before the gate blocks further
705    /// service as a defence-in-depth backstop.
706    ///
707    /// A ceiling enforced by `ServiceGate::acquire` while the current front is funded. A
708    /// [`crate::HoprSessionInPixEvent::RecoveryProgress`] snapshot resets it only for that funded
709    /// front. The sole recovered predecessor temporarily remains that paid front while its
710    /// per-polynomial negotiated remainder drains; progress on an unfunded, queued, older, or
711    /// over-budget cycle does not grant service.
712    ///
713    /// Those events now follow `shares_seen` rather than `useful_shares`, which is what makes a flat
714    /// 2048 safe at any dimensions. Keyed on useful shares, this had to exceed
715    /// `surplus x min(polys, SHARE_EMISSION_WINDOW)` — 4096 at the shipped dimensions, twice
716    /// this value — because a conforming Entry emits a whole window's surplus in one contiguous run
717    /// during which no share is useful. The gate parked the writer partway through, and a parked
718    /// writer spends no SURBs, so nothing could arrive to release it. See
719    /// [`SsaRecoveryProgress::shares_seen`](hopr_protocol_pix::SsaRecoveryProgress::shares_seen).
720    ///
721    /// What it bounds now is genuine silence, and that is rate-independent: it is a count of
722    /// *packets*, so unlike [`max_recovery_idle`](Self::max_recovery_idle) it implies no throughput
723    /// floor.
724    ///
725    /// Default: 2048 packets.
726    #[default(2048)]
727    pub max_served_without_progress: u64,
728
729    /// How long to retain recovered-SSA diagnostic records and observer ownership.
730    ///
731    /// Must be >= the reconstructor's `max_ack_await_time`. The compact paid-tail receipt is separate
732    /// and may outlive this record; expiring a tombstone therefore does not truncate a FIFO drain.
733    ///
734    /// Default: 30 s.
735    #[default(Duration::from_secs(30))]
736    #[serde(with = "humantime_serde")]
737    pub tombstone_retention_window: Duration,
738}

889/// Validates that [`SupervisorConfig`] and [`SsaReconstructorConfig`] are
890/// mutually consistent.
891///
892/// Returns an error if constraints are violated.
893pub fn validate_pix_supervision(
894    cfg: &SupervisorConfig,
895    reconstructor_cfg: &SsaReconstructorConfig,
896) -> Result<(), TransportSessionError> {
897    if !(1..=crate::MAX_SSA_BATCH_SIZE).contains(&cfg.ssas_per_request) {
898        return Err(TransportSessionError::InvalidConfig(format!(
899            "ssas_per_request ({}) must be between 1 and {}",
900            cfg.ssas_per_request,
901            crate::MAX_SSA_BATCH_SIZE
902        )));
903    }
904    // Zero would close the Session on the first lost cycle *and* on the last one standing, which is
905    // the same thing at the shipping batch size but silently disables batching above it. The
906    // supervisor clamps to one where it reads this; rejecting here is what an operator sees.
907    if cfg.max_failed_cycles == 0 {
908        return Err(TransportSessionError::InvalidConfig(
909            "max_failed_cycles must be non-zero".into(),
910        ));
911    }
912    if cfg.max_ssa_delivery_time.is_zero() {
913        return Err(TransportSessionError::InvalidConfig(
914            "max_ssa_delivery_time must be non-zero".into(),
915        ));
916    }
917    if cfg.max_deposit_wait.is_zero() {
918        return Err(TransportSessionError::InvalidConfig(
919            "max_deposit_wait must be non-zero".into(),
920        ));
921    }
922    if cfg.max_recovery_idle.is_zero() {
923        return Err(TransportSessionError::InvalidConfig(
924            "max_recovery_idle must be non-zero".into(),
925        ));
926    }
927    if cfg.max_recovery_time.is_zero() {
928        return Err(TransportSessionError::InvalidConfig(
929            "max_recovery_time must be non-zero".into(),
930        ));
931    }
932    if cfg.tombstone_retention_window.is_zero() {
933        return Err(TransportSessionError::InvalidConfig(
934            "tombstone_retention_window must be non-zero".into(),
935        ));
936    }
937    if cfg.max_served_without_progress == 0 {
938        return Err(TransportSessionError::InvalidConfig(
939            "max_served_without_progress must be non-zero".into(),
940        ));
941    }
942    // A fraction outside 0..=1 is unreachable rather than strict — the ratio can never exceed 1 — so a
943    // typo would silently disable the check instead of tightening it.
944    if !cfg.max_off_front_share_fraction.is_finite() || !(0.0..=1.0).contains(&cfg.max_off_front_share_fraction) {
945        return Err(TransportSessionError::InvalidConfig(format!(
946            "max_off_front_share_fraction ({}) must be a fraction between 0.0 and 1.0",
947            cfg.max_off_front_share_fraction
948        )));
949    }
950    // Zero would judge the very first off-front share, which mixnet reordering alone can produce.
951    if cfg.min_share_order_sample == 0 {
952        return Err(TransportSessionError::InvalidConfig(
953            "min_share_order_sample must be non-zero".into(),
954        ));
955    }
956    if cfg.max_recovery_idle < reconstructor_cfg.max_ack_await_time {
957        return Err(TransportSessionError::InvalidConfig(
958            "max_recovery_idle must be >= max_ack_await_time".into(),
959        ));
960    }
961    // An Exit below the floor asks for its next batch before any conforming Entry will admit the
962    // request. The Entry's gate is computed at the floor precisely because this value does not travel
963    // on the wire (see `MIN_EARLY_RECOVERY_THRESHOLD`), so the mismatch cannot be detected on the
964    // link: the one-shot request is dropped, nothing acknowledges the refusal, and the Session dies
965    // on `max_ssa_delivery_time` waiting for a commitment that was deliberately withheld. Rejecting
966    // it here turns a silent remote failure into a local startup error, which is the only place the
967    // operator who set the value can see it.
968    //
969    // Written as a range rather than `< floor`, and with the finiteness test in front, for the same
970    // reason `max_off_front_share_fraction` above is: every IEEE comparison against `NaN` is false, so
971    // `NaN < floor` admits it, and a `NaN` threshold is not inert — `ceil` leaves it `NaN` and casting
972    // that to an integer saturates to zero, so the Exit signals early recovery on its first
973    // reconstructed polynomial. That is the *earliest* possible request against a gate whose entire
974    // job is to refuse early ones.
975    if !reconstructor_cfg.early_recovery_threshold.is_finite()
976        || !(hopr_protocol_pix::MIN_EARLY_RECOVERY_THRESHOLD..=1.0)
977            .contains(&reconstructor_cfg.early_recovery_threshold)
978    {
979        return Err(TransportSessionError::InvalidConfig(format!(
980            "early_recovery_threshold ({}) must be a finite fraction between MIN_EARLY_RECOVERY_THRESHOLD ({}) and \
981             1.0; a lower value asks for the next SSA batch before a conforming Entry admits the request",
982            reconstructor_cfg.early_recovery_threshold,
983            hopr_protocol_pix::MIN_EARLY_RECOVERY_THRESHOLD
984        )));
985    }
986    // Documented invariant: tombstone must outlive the ack window.
987    if cfg.tombstone_retention_window < reconstructor_cfg.max_ack_await_time {
988        return Err(TransportSessionError::InvalidConfig(
989            "tombstone_retention_window must be >= max_ack_await_time (otherwise late acks arrive after the tombstone \
990             expires)"
991                .into(),
992        ));
993    }
994    // The supervisor must give up on a stalled SSA before the reconstructor reclaims the state it
995    // would need to finish one. Written against `unused_verifier_lifetime` because that is now the
996    // only duration governing a live cycle: it is measured from the last acknowledged share
997    // *anywhere* in the cycle, so a cycle that is still being served never expires and the two
998    // deadlines only ever race on a cycle that has genuinely stopped.
999    //
1000    // This replaces a comparison against `incomplete_ssa_lifetime`, which no longer exists. That
1001    // field was inert in any case — it was clamped to the larger of the two lifetimes, so the
1002    // default configuration always resolved it to 1800 s rather than its own 600 s — which is
1003    // exactly the kind of hand-held lifetime pairing that scoping reclamation to the cycle removed.
1004    if cfg.max_recovery_idle >= reconstructor_cfg.unused_verifier_lifetime {
1005        return Err(TransportSessionError::InvalidConfig(
1006            "max_recovery_idle must be < unused_verifier_lifetime".into(),
1007        ));
1008    }
1009    // Reject durations that would overflow the monotonic clock when used as
1010    // deadlines. See `MAX_SUPERVISOR_DURATION`.
1011    //
1012    // The first two are checked *as armed*, i.e. multiplied by the batch size, because that product
1013    // is the duration a deadline is actually set to. Checking the unscaled value would let a config
1014    // pass here and then be silently clamped at arming time, which is the failure mode this cap
1015    // exists to make loud.
1016    //
1017    // The other three are not scaled, so the scaling fact travels per entry rather than being
1018    // asserted for the whole loop. A blanket "as armed for a batch of N" invites the operator to
1019    // divide the reported figure by N and conclude they configured a value they did not — which is
1020    // the same class of misdirection the cap exists to prevent.
1021    for (name, dur, scaled) in [
1022        (
1023            "max_ssa_delivery_time",
1024            scaled_deadline(cfg.max_ssa_delivery_time, cfg.ssas_per_request),
1025            true,
1026        ),
1027        (
1028            "max_deposit_wait",
1029            scaled_deadline(cfg.max_deposit_wait, cfg.ssas_per_request),
1030            true,
1031        ),
1032        ("max_recovery_idle", cfg.max_recovery_idle, false),
1033        ("max_recovery_time", cfg.max_recovery_time, false),
1034        ("tombstone_retention_window", cfg.tombstone_retention_window, false),
1035    ] {
1036        if dur > MAX_SUPERVISOR_DURATION {
1037            let armed = if scaled {
1038                format!(", as armed for a batch of {}", cfg.ssas_per_request)
1039            } else {
1040                String::new()
1041            };
1042            return Err(TransportSessionError::InvalidConfig(format!(
1043                "{name} ({dur:?}{armed}) must not exceed {MAX_SUPERVISOR_DURATION:?}"
1044            )));
1045        }
1046    }
1047    // The two recovery clocks measure different things and only one of them is an anti-drip rule.
1048    // `max_recovery_idle` is service-gated, so it spares a Session that is merely quiet and closes
1049    // one that is consuming service while returning nothing. `max_recovery_time` is neither gated nor
1050    // refreshable — it is a resource backstop for the slot and the reconstructor state, and is
1051    // documented as such throughout this module.
1052    //
1053    // Set at or below the idle deadline, the backstop fires first on *every* cycle. The idle rule —
1054    // the only instrument that can tell a slow honest Session from a cheating one — becomes
1055    // unreachable, and honest Sessions are closed on `RecoveryDeadline` instead. Both values pass
1056    // every check above individually, so this inversion is invisible unless the two are compared.
1057    //
1058    // Checked after the cap loop deliberately. An over-cap `max_recovery_idle` cannot satisfy this
1059    // rule either — no legal `max_recovery_time` exceeds it — so running this first would make the
1060    // cap's own `max_recovery_idle` branch unreachable and swap a precise diagnostic for a vaguer
1061    // one. Representability first, then policy.
1062    if cfg.max_recovery_time <= cfg.max_recovery_idle {
1063        return Err(TransportSessionError::InvalidConfig(format!(
1064            "max_recovery_time ({:?}) must be > max_recovery_idle ({:?}); the hard deadline is a resource backstop, \
1065             and at or below the idle deadline it pre-empts the service-gated idle rule on every cycle",
1066            cfg.max_recovery_time, cfg.max_recovery_idle
1067        )));
1068    }
1069    Ok(())
1070}

1072/// Upper bound on any supervisor duration, as it is actually armed.
1073///
1074/// 24 h is far above anything a supervisor deadline should be, and the point is not the number but
1075/// the failure it forecloses: every phase reads an absent deadline as *no deadline*, and
1076/// `Instant::checked_add` returns `None` for a duration the monotonic clock cannot represent. So a
1077/// large enough configured value does not produce a long deadline, it produces none at all — the
1078/// supervisor silently stops enforcing that phase.
1079///
1080/// Enforced twice, and deliberately so. [`validate_pix_supervision`] *rejects* a config above it,
1081/// which is what an operator should see. `SessionManager::new` *clamps* to it, because nothing in
1082/// this crate calls `validate` and a programmatically assembled config would otherwise reach the
1083/// supervisor unchecked.
1084pub(crate) const MAX_SUPERVISOR_DURATION: Duration = Duration::from_secs(86400);
1085
1086/// A per-cycle deadline duration as it is actually armed for a batch of `ssas_per_request`.
1087///
1088/// One place computes this so the validator and the supervisor cannot disagree about what a
1089/// configuration means. `ssas_per_request` is clamped rather than trusted, because a supervisor can be
1090/// constructed from a config that never went through [`validate_pix_supervision`]; the multiplication
1091/// saturates for the same reason.
1092pub(crate) fn scaled_deadline(per_cycle: Duration, ssas_per_request: usize) -> Duration {
1093    per_cycle.saturating_mul(ssas_per_request.clamp(1, crate::MAX_SSA_BATCH_SIZE) as u32)
1094}
