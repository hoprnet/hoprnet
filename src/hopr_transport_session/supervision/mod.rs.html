1//! PIX supervision for incoming PIX-enabled sessions.
2//!
3//! This module implements the **Exit-side** supervision logic for sessions
4//! using the Protocol for Incentivization of eXits (PIX).  The Exit node
5//! runs a deterministic supervisor that tracks each *Secret Sharing Aggregate*
6//! (SSA) through a well-defined lifecycle, enforcing timeouts, deposit
7//! sufficiency, recovery progress, and fault tolerances.  Egress data
8//! packets are gated behind a concurrent `ServiceGate` that follows the
9//! front cycle: bounded predeposit service while it is unfunded and a
10//! ceiling-limited path after it funds.
11//!
12//! # Why supervision is needed
13//!
14//! PIX sessions use SSAs: cryptographic aggregates that distribute the
15//! cost of a deposit across many packets sent from the Entry to the Exit.
16//! Each SSA requires:
17//!
18//! 1. A **commitment** from the Entry (polynomial coefficients) that the Exit can verify.
19//! 2. A **deposit** to an SSA-specific on-chain address before the Exit fully trusts the SSA.
20//! 3. **Recovery** of the SSA shares from data packets as they arrive.
21//!
22//! Without supervision, a misbehaving or stalled Entry can hold a session
23//! slot indefinitely without ever funding or completing recovery — a
24//! resource-exhaustion vector.  The supervisor enforces hard per-SSA and
25//! per-session bounds so the Exit can reclaim resources deterministically.
26//!
27//! # Architecture
28//!
29//! The module is split into three components:
30//!
31//! | Component | File | Role |
32//! |---|---|---|
33//! | `SessionPixSupervisor` | `supervisor` | Pure state machine — no I/O, no async, no spawning.  Driven by explicit `Instant` timestamps and service-gate snapshots. |
34//! | `ServiceGate` | `gate` | Concurrent, lock-free egress gate.  Before the front funds: bounded predeposit budget.  After it funds: ceiling on packets served without that cycle's recovery progress.  Callers park on a generation-counter waker. |
35//! | `FillPlanner` | `fill` | Pure rate law for the Exit's own keep-alives.  Answers, once a second, how fast this node must send in order for the funded cycle to complete inside its deadline — and emits nothing when the answer has not meaningfully changed. |
36//! | Worker loop | `worker` | Per-session actor that bridges the pure supervisor to async reality.  Receives commands via a backpressured channel, manages the deadline and fill timers, applies gate actions synchronously, and forwards actions to the caller. |
37//!
38//! The [`SlotNotify`](crate::utils::SlotNotify) multi-waker primitive is shared from [`utils`] and used
39//! by `ServiceGate` to park and wake callers without a tokio dependency.
40//!
41//! ## The `SessionPixSupervisor` state machine
42//!
43//! The supervisor tracks each SSA through these phases:
44//!
45//! ```text
46//! RequestSsa  ──►  SsaRequestSent  ──►  AwaitingCommitment
47//!                                          ├── (CommitmentProgress arms/re-arms the re-request timer)
48//!                                          ├── (its expiry → RequestCommitmentRetransmission, bounded)
49//!                                          │
50//!                                     CommitmentVerified
51//!                                          │
52//!                                      AwaitingDeposit
53//!                                          │
54//!                                     DepositConfirmed (≥ expected)
55//!                                          │
56//!                                        Recovering
57//!                                          ├── (idle re-arms when no service)
58//!                                          ├── hard deadline is immutable
59//!                                          └── progress resets idle timer
60//!                                          │
61//!                                     Recovered
62//!                                          ├── bounded paid FIFO drain
63//!                                          ├── successor progress → handoff
64//!                                          └── diagnostic tombstone expiry → RetireSsa
65//! ```
66//!
67//! **Key deadlines** (all configurable via [`SupervisorConfig`]):
68//!
69//! * **Commitment timeout** — time from `SsaRequestSent` to `CommitmentVerified`.
70//! * **Commitment re-request** — time a *partially* delivered commitment may go quiet before the missing parts are
71//!   asked for again. The one deadline here that is not a deadline: it emits a repair and re-arms, never a close, and
72//!   the commitment timeout above remains the bound. It is armed only by `CommitmentProgress`, so a commitment nothing
73//!   was ever delivered for never asks — there is no scope for it to name. Bounded by count, at
74//!   [`MAX_COMMITMENT_RETRANSMISSIONS`](hopr_protocol_pix::MAX_COMMITMENT_RETRANSMISSIONS), which is what the Entry
75//!   will answer.
76//! * **Deposit timeout** — time from `CommitmentVerified` to a sufficient deposit.
77//! * **Recovery idle** — time without *any share arriving* while service is being consumed. **Service-gated**: if no
78//!   packets were served since the last progress snapshot, the timer re-arms instead of closing (prevents a
79//!   slow-but-honest Entry from being disconnected). Deliberately not "useful progress": a conforming Entry emits a
80//!   whole window's surplus in one run, none of it useful, and treating that as silence closes honest Sessions.
81//! * **Recovery hard deadline** — absolute per-SSA backstop, never extended. This is a resource guard (session slot +
82//!   reconstructor memory), not a liveliness mechanism.
83//!
84//! Both recovery clocks start when the cycle reaches the **paid transport front**, not when its
85//! deposit confirms. A batch is served in index order, and the final SURBs buffered for a recovered
86//! predecessor still carry that predecessor's shares. The predecessor keeps its original immutable
87//! hard clock while this bounded tail drains; the successor's clocks start only when the negotiated
88//! remainder is exhausted or funded successor progress proves the FIFO boundary. A queued cycle is
89//! therefore not charged for either its batch wait or its predecessor's pipeline delay.
90//!
91//! **Fault tracking** — an `UnverifiableShares` event closes the Session on arrival, with no
92//! tolerance to configure and no running totals to keep: the event means a polynomial's share set
93//! failed to open its commitment, which permanently dooms the cycle. Late fault reports against an
94//! already terminal SSA are absorbed. Progress is the one narrow exception: the sole immediate
95//! recovered predecessor may report its bounded, already-paid FIFO tail. See the configuration
96//! section below for why this is not a dial.
97//!
98//! **Rolling SSAs** — to maintain continuity, the supervisor requests the *next* batch when the
99//! current one is "almost recovered" (early threshold reached) or fully recovered, so the commitment
100//! and deposit work for the next cycle overlaps the tail of the current one. With a batch, only its
101//! **last** cycle may ask: the request flags are per-cycle, so without that gate every member would
102//! answer its own early signal with a batch of its own, compounding into `ssas_per_request` batches
103//! per batch. The last rather than the first, because a batch is served in index order and gating on
104//! the first would ask a whole batch too early. Retiring the cycle holding the gate hands it to the
105//! newest survivor, or a batch whose last cycle lost its deposit would strand with no successor.
106//!
107//! Allocation independently enforces the reservation: at most
108//! `MAX_OVERLAPPING_BATCHES` generations and
109//! `MAX_OVERLAPPING_BATCHES × ssas_per_request` live cycles may own reconstructor state. If the
110//! early signal arrives while both generations are still live, the supervisor records the owed
111//! request and retries it only after one generation releases its heavyweight cycle state. Recovered
112//! supervisor tombstones do not count because full recovery removes their heavyweight reconstructor
113//! state; one constant-bounded per-Session tail receipt is tracked separately.
114//!
115//! ## The `ServiceGate` — egress gating
116//!
117//! Every egress data packet from the Exit back to the Entry must pass
118//! through the `ServiceGate` via `acquire`:
119//!
120//! ### Pre-funding (predeposit)
121//!
122//! While the current front cycle is unfunded, a provisional budget lets the Exit answer the Entry
123//! for a bounded number of packets, so that the application is not held up for as long as an
124//! on-chain deposit takes to confirm. The initial front starts with this allowance; a successor gets
125//! a fresh allowance after its predecessor was funded and leaves the front, whether by recovery or a
126//! tolerated failure. A failed funded cycle has already cost the Entry its full deposit, and
127//! `max_failed_cycles` bounds how often that can happen. Losing an unfunded front does not mint
128//! another grant. The budget is
129//! `min(target_useful_shares - 1, max_predeposit_packets)`; at production dimensions the first term
130//! is in the hundreds of thousands, so the configured cap is what binds and the `min` only matters
131//! for the small dimensions used in tests.
132//!
133//! When the budget is exhausted, `acquire` parks the caller on a
134//! `SlotNotify` future. A concurrent `release_service`, `withhold_service`,
135//! `notify_progress`, or `poison`
136//! wakes all parkers.
137//!
138//! ### Strict prepay (`max_predeposit_packets = 0`)
139//!
140//! Zero is a supported setting, and it means the Exit serves nothing against any unfunded front:
141//! the first egress data packet parks, and the Entry has to commit and fund that cycle before a
142//! single payload byte flows back to it. The rule is restored on every paid rotation rather than
143//! applying only to the Session's first SSA.
144//!
145//! This does not deadlock, because nothing on the path to funding passes through the gate:
146//!
147//! * The `SsaRequest` goes out on the [`SessionManager`]'s own message sender, not the Session's gated sink.
148//! * The Entry's commitment travels Entry→Exit, and the deposit is on-chain.
149//! * The SURB-level keep-alive stream is deliberately left ungated, precisely so an exhausted budget cannot silence the
150//!   signal that keeps the Session fundable. Under strict prepay this carries more weight than it does at a non-zero
151//!   budget: with no egress at all, the keep-alives are the *only* traffic reaching the Entry, and therefore the only
152//!   thing resetting the idle timer on the Entry's own session slot. An operator who both sets this budget to zero and
153//!   disables `surb_balance_notify_period` gives the Entry nothing to stay alive on, and it will evict the Session
154//!   before a deposit can land.
155//!
156//! So the Entry can always be asked for a deposit and can always answer, whatever the budget is.
157//! What a zero budget costs is latency, not liveness: the application stalls until the deposit
158//! confirms, instead of proceeding optimistically. If the deposit never arrives, the deposit
159//! deadline closes the Session and `poison` fails the parked writer rather
160//! than leaving it pending.
161//!
162//! ### Post-funding (ceiling)
163//!
164//! Once the current front's deposit is confirmed and the supervisor emits `ReleaseService`, the
165//! gate flips to funded mode. It then enforces `max_served_without_progress`: a
166//! ceiling on how many packets may be served between SSA recovery progress
167//! events, as a defense-in-depth backstop even when the supervisor's
168//! service-gated idle timer is alive. Only progress from that funded front—or from its sole bounded
169//! recovered predecessor while the FIFO drains—emits `ProgressNotification` and resets the
170//! watermark; unfunded, off-front, older, or over-budget progress cannot buy service. A rotation to
171//! an unfunded successor emits `WithholdService` and restores the bounded allowance. A funded
172//! successor stays open, but another `ReleaseService` rebaselines its ceiling.
173//!
174//! The gate is implemented with lock-free atomics and CAS loops.  It uses
175//! the generation-counter `SlotNotify` to avoid the two classic
176//! race conditions of waker-vector approaches:
177//!
178//! 1. **Latent wake** — notification between future creation and first `poll()` is caught because the generation was
179//!    captured at creation time and compared on `poll()`.
180//! 2. **Spurious `Ready`** — a second `poll()` of an already-registered future re-checks the generation; if unchanged
181//!    it stays `Pending`.
182//!
183//! ## Fill — keeping a funded cycle on course
184//!
185//! Everything above is a rule for *stopping*. This is the one rule for going, and it exists because
186//! the rules for stopping cannot be met by an idle Session.
187//!
188//! ### What goes wrong without it
189//!
190//! A PIX Exit is paid per **return** packet. Each Exit → Entry packet spends one SURB carrying one
191//! share, and a funded cycle recovers — unlocks the deposit key it has already been paid for — only
192//! once `polys × (threshold + surplus)` of them have gone back. That is 327 680 packets at the shipped
193//! dimensions. Nothing in the protocol makes the *application* send them:
194//!
195//! * an idle VPN client sends nothing at all;
196//! * a tunnel between keystrokes sends a handful a minute;
197//! * any client that reads more than it writes returns fewer packets than it receives, by definition.
198//!
199//! Each of those leaves the Exit holding a cycle it was paid for and cannot complete.
200//! [`max_recovery_time`](SupervisorConfig::max_recovery_time) then closes the Session, and because
201//! the deposit address derives from the client's and the server's commitments *together*, the money
202//! is stranded rather than refunded. At production geometry the boundary is about 46 return packets
203//! per second averaged over a whole cycle — which is not a light client, it is a saturated one.
204//!
205//! So the Exit sends its own. The rate is planned once per `SAMPLING_INTERVAL`:
206//!
207//! ```text
208//! E          = polys × (threshold + surplus)                          packets in one cycle
209//! target     = the recovered predecessor's paid FIFO tail if there is one, else the earliest
210//!              live cycle that is both funded and clocked, else none → rate 0
211//! remaining  = (E − shares seen on the target) × (1 + loss_margin)
212//! finish_by  = target.hard_deadline − (1 − finish_fraction) × max_recovery_time
213//! required   = remaining / max(finish_by − now, SAMPLING_INTERVAL)     packets/s
214//! organic    = EMA over ORGANIC_WINDOW of the service gate's counter   packets/s
215//! fill       = clamp(required − organic, heartbeat, max_rate)
216//! ```
217//!
218//! The tail wins over the successor whenever it exists, for two reasons that point the same way: its
219//! SURBs sit ahead of the successor's in the Exit's own buffer, so packets sent now carry *its*
220//! shares; and it holds the binding deadline, since the successor's clocks are deliberately not armed
221//! until the tail is exhausted.
222//!
223//! ### Why it is the keep-alive message
224//!
225//! Fill reuses the Exit's SURB-level keep-alive rather than introducing a message of its own, and the
226//! two share one stream and one rate controller running at the faster of the two. Every shipped Entry
227//! already parses that message, already counts it as a consumed SURB so its balancer refills, and
228//! already credits it as service against the successor gate — so an Exit that fills needs nothing new
229//! from its peer. A new flag bit would have been worse than useless: keep-alive flag decoding used to
230//! be strict, so a bit an older Entry did not recognise made the whole message fail to parse.
231//!
232//! ### What bounds it
233//!
234//! A rule that *sends* is the one rule in this module that could be turned against the node running
235//! it, so it is bounded four times over:
236//!
237//! | Bound | What it stops |
238//! |---|---|
239//! | [`max_rate`](PixFillConfig::max_rate) | The instantaneous cost of one Session. Validated *upwards* too — `validate_incoming_session_pix_config` refuses a ceiling below the rate the widest accepted quota needs, because a filler that cannot finish is worse than none. |
240//! | [`min_surb_reserve`](PixFillConfig::min_surb_reserve) | Fill spending the SURBs the Session needs for its own replies. Not an optimisation: a return packet that finds no SURB holds every packet this node originates for `surb_resolution_wait`, so an over-eager filler stalls the Session it is saving. The SURB-level notification is exempt, being the message that asks for more. A ceiling rather than the figure used — the buffer it is measured against is the Entry's choice, so the effective reserve is never more than a quarter of the target the Entry announced. |
241//! | The stall rule | A doomed cycle, or a share-less SURB supply, burning `max_rate × max_recovery_time`. Once the target has not moved for [`max_recovery_idle`](SupervisorConfig::max_recovery_idle), fill drops to its heartbeat until the cycle moves again. |
242//! | The existing deadlines and the service gate | Unchanged. Fill is not a way around the backstop: an Exit with nothing to send strands exactly as it did before. |
243//!
244//! The stall rule cannot be delegated to `max_recovery_idle` itself, and that is worth being explicit
245//! about. The idle rule re-arms whenever no *gated* service was consumed since the last progress, and
246//! fill bypasses the gate exactly as the keep-alive stream it reuses does — so a Session whose only
247//! traffic is fill looks perfectly quiet to it and it never fires. The stall rule is the bound the
248//! gate-based one cannot supply.
249//!
250//! ### What it costs the client
251//!
252//! One cycle's quota per deadline while idle, and nothing at all while the application is busier than
253//! the required rate. The client accepts that as the price of a Session whose cycles complete, and
254//! funds successors as it would have.
255//!
256//! ## The Worker — bridging pure logic to async
257//!
258//! `spawn_supervisor_worker` creates the `SessionPixSupervisor`,
259//! the `ServiceGate`, and a bounded async command channel.  It returns
260//! a `SessionPixSupervisorHandle` (cloneable, for sending events) and an
261//! `ActionRx` receiver (for driving actions).
262//!
263//! The worker loop:
264//!
265//! 1. Reads the earlier of the next deadline and the next fill tick from the supervisor.
266//! 2. If it has already passed, calls `handle_timers` immediately.
267//! 3. Otherwise, waits on the command channel with a timeout set to the remaining duration.
268//! 4. On command received → calls `handle_event` or `action_result`.
269//! 5. On timeout → calls `handle_timers`, which runs the deadline sweep first and then the fill tick if one is due. The
270//!    order matters: the sweep is what arms a promoted cycle's clocks and consumes a spent FIFO tail, so a tick that
271//!    ran first would plan against a lifecycle one interval out of date.
272//! 6. Applies gate-control actions immediately, then forwards all actions to the action channel (non-blocking
273//!    `try_send`).
274//!
275//! A Session with no funded cycle to fill for schedules no tick at all, so the loop's behaviour is
276//! byte-for-byte what it was before fill existed until the first deposit confirms.
277//!
278//! **Coalescing** — `ProgressNotification` actions are coalescible: when
279//! the action channel is transiently full, they are dropped rather than
280//! blocking or failing the worker. The gate has already consumed the notification locally, and the
281//! next forwarded notification replaces it for observers.
282//!
283//! All other actions (`RequestSsa`, `ReleaseService`, `WithholdService`, `RetireSsa`, `SetFillRate`,
284//! `Close`) are non-coalescible — if they cannot be delivered, the channel is
285//! genuinely wedged and the worker fails the session. `SetFillRate` belongs on that side of the line
286//! even though it arrives on a timer: the planner's hysteresis means it will not re-emit a value it
287//! believes is already applied, so a dropped change is not replaced by the next one — and the worst
288//! case is a dropped zero, which leaves a Session filling for a cycle that no longer exists.
289//!
290//! ## Integration with [`SessionManager`]
291//!
292//! ### Exit side (incoming sessions)
293//!
294//! When `handle_incoming_session_initiation` processes a session request
295//! with `Capability::UsePIX`:
296//!
297//! 1. Validates the offered PIX parameters (polys, threshold, quota range).
298//! 2. Spawns the supervisor worker via `spawn_supervisor_worker` (this emits the initial `RequestSsa` action and
299//!    creates the gate).
300//! 3. Reads the initial action, calls `send_ssa_request` on the wire, and notifies the supervisor of `SsaRequestSent`.
301//! 4. Stores the supervisor handle and gate in the session slot (via `OnceLock`).
302//! 5. Constructs the [`HoprSession`] — the egress adapter acquires the gate on every outgoing data packet.
303//! 6. After session publication, spawns the **action driver task** that receives actions from `ActionRx`. Gate control
304//!    has already happened in the worker; the driver performs I/O and records the gate-mode telemetry:
305//!
306//!    | Action | Behaviour |
307//!    |---|---|
308//!    | `RequestSsa` | Calls `send_ssa_request`, feeds back result to supervisor. Tracks each SSA in `SsaCommitmentGuard` for Drop-safe cleanup. |
309//!    | `RequestCommitmentRetransmission` | Calls `send_commitment_retransmission_request`, which reads the missing scope from the reconstructor and asks the Entry for it. Registers nothing and reports nothing back: it repeats on its own interval and the commitment deadline is the backstop. |
310//!    | `ReleaseService` | Worker calls `gate.release_service()`; driver records funded telemetry. |
311//!    | `WithholdService` | Worker calls `gate.withhold_service()`; driver records unfunded telemetry. |
312//!    | `ProgressNotification` | Worker calls `gate.notify_progress()`; no driver I/O. |
313//!    | `RetireSsa` | Calls `share_processor.retire_ssa`, aborts the deposit observer task. |
314//!    | `SetFillRate` | Applies the rate to the Session's shared keep-alive controller and records the gauge. |
315//!    | `Close` | Silences fill, poisons gate, retires all SSAs, publishes close metric, removes session slot. |
316//!
317//! 7. PIX protocol events from the packet pipeline arrive via `dispatch_pix_event` and are forwarded to the supervisor
318//!    as `SessionPixEvent::RecoveryProgress`, `UnverifiableShares`, `AlmostRecovered`, or `Recovered`.
319//! 8. When a commitment becomes verifiable, a `PixDepositObserver` task loops on deposit confirmations, forwarding each
320//!    as `DepositConfirmed` to the supervisor.
321//!
322//! ### Entry side (outgoing sessions)
323//!
324//! The Entry does **not** run a supervisor — the Exit is authoritative for
325//! lifecycle decisions.  The Entry creates a session slot when
326//! `new_session()` succeeds, but the slot's `pix_supervisor` and
327//! `pix_egress_gate` remain unpopulated.  On receiving an `SsaRequest`
328//! from the Exit, the Entry generates its client commitment via the
329//! share generator, sends the commitment messages, and emits
330//! `ReadyToDeposit` so the caller can fund the deposit address.
331//!
332//! ## Lifecycle sketch (Exit side)
333//!
334//! ```text
335//! Session Initiation (Entry→Exit, with UsePIX flag)
336//!     │
337//!     ▼
338//! handle_incoming_session_initiation
339//!     │  validate PIX params
340//!     │  spawn supervisor (emits initial RequestSsa)
341//!     │  send SsaRequest on the wire
342//!     │  install gate & handle in slot
343//!     │  construct HoprSession (egress adaptor acquires gate)
344//!     │  spawn action driver
345//!     ▼
346//! ┌────────────────────────────────────────────────────┐
347//! │  Ongoing lifecycle (concurrent)                    │
348//! │                                                    │
349//! │  Entry → CommitmentVerified  → supervisor          │
350//! │  Entry → DepositConfirmed    → supervisor (via     │
351//! │                                PixDepositObserver) │
352//! │  Packets → share_processor   → RecoveryProgress    │
353//! │  Action: ReleaseService       → gate.release_service│
354//! │  Action: WithholdService      → gate.withhold_service│
355//! │  Action: ProgressNotification → gate.notify_progress│
356//! │  Action: RequestSsa (next)   → send on wire        │
357//! │  Action: RetireSsa           → reconstructor.retire│
358//! │  Action: Close               → poison + teardown   │
359//! └────────────────────────────────────────────────────┘
360//! ```

362//! # Configuration
363//!
364//! ## What each parameter prevents
365//!
366//! Every field of [`SupervisorConfig`], the failure it exists to stop, and what shipping default it
367//! carries. Nothing here is a preference: each one is the only thing standing between the Exit and a
368//! specific way of taking service without paying for it.
369//!
370//! | Parameter | Default | What it prevents |
371//! |---|---|---|
372//! | `ssas_per_request` | 1 | Nothing by itself — an exposure dial. With dynamic batching it is the largest batch the Exit may derive; otherwise it is the exact batch size. Raising it amortises the request round trip over several cycles, at the price of multiplying the *unfunded* exposure to that many quotas, and it scales the two deadlines below. |
373//! | `allow_dynamic_ssa_batches` | true | Lets a sub-range per-SSA offer satisfy `quota_range` by committing to the smallest batch whose total quota enters the range. Disable it to retain the fixed-batch, per-SSA admission rule. |
374//! | `max_failed_cycles` | 1 | An Entry losing one cycle per batch indefinitely while a single funded sibling holds the Session open. One loss is survivable, the second closes the Session. Only reachable above a batch of one, where the failing cycle is not always the last one standing. |
375//! | `max_ssa_delivery_time` | 20 s | An Entry that accepts a request and never delivers the commitment set, holding a session slot and a reconstructor cycle that can never be funded. |
376//! | `commitment_recommit_interval` | 3 s | A *single lost packet* costing the whole Session. A commitment set ships as hundreds of messages and is unusable until every one lands, so without this a drop stranded the cycle on the deadline above — after the Entry had already been told to fund it. The one parameter here that buys liveness rather than bounding an attack; it bounds nothing itself. |
377//! | `max_deposit_wait` | 60 s | An Entry that commits but never deposits — typically after it has already drawn the predeposit budget. |
378//! | `max_recovery_idle` | 60 s | An Entry, or a colluding first return relayer, consuming service while returning no shares. Service-gated, so a Session that is merely quiet is never punished. |
379//! | `max_recovery_time` | 2 h | A cycle that dribbles just enough progress to refresh the idle timer forever. A resource backstop for the slot and the reconstructor state, *not* the anti-drip rule. It must clear a whole cycle at the widest dimensions the node accepts — 655 360 packets of *full emission*, ~61 min, at the defaults — or it closes honest Sessions instead. That is the quantity `quota_range` prices and `validate_incoming_session_pix_config` enforces; the *last useful share* lands earlier, at 651 264, which is the figure the "why two hours" argument on [`SupervisorConfig::max_recovery_time`] uses. |
380//! | `max_off_front_share_fraction` | 0.25 | An Entry spreading a batch's shares across all of its cycles, taking `ssas_per_request` quotas of service while completing none of them — and a cycle short of completion pays nothing at all. |
381//! | `min_share_order_sample` | 16384 | Convicting on a thin sample: the shares that legitimately cross a cycle boundary out of order while in flight. |
382//! | `max_predeposit_packets` | 10000 | Bounds what an Entry can extract from an unfunded front. Restored only after a paid front handoff; `0` means strict prepay on every rotation. |
383//! | `max_served_without_progress` | 2048 | Packets served with no share of *any* kind coming back — in *packets*, so unlike the idle timer the bound does not move with the Session's rate. Counts `shares_seen`, so a conforming Entry's surplus resets it; see below. |
384//! | `tombstone_retention_window` | 30 s | Bounds how long recovered-cycle diagnostics and observer ownership remain; the separately bounded FIFO-tail receipt may outlive it. |
385//! | `fill` | on | The one rule here that *sends* rather than stops: a funded cycle only recovers once its whole emission has ridden back to the Entry, so an idle Session strands the deposit it has already been paid. See [`PixFillConfig`]. |
386//!
387//! ## What is *not* here: the price of a cycle
388//!
389//! No parameter above says what a quota costs, and none should. The Exit's deposit pool is handed the
390//! [`DepositUpdated`](hopr_api::node::DepositUpdated) sender along with
391//! [`AgreedSsaQuota`] when the deposit address arrives, and it is the component
392//! that knows both the byte quota and the price it charges for one. It sends on that channel once the
393//! deposit clears that price; the supervisor's `DepositConfirmed` handler acts on the verdict rather
394//! than recomputing it. The Entry side mirrors this — its own strategy prices the `quota` carried by
395//! `PixEvent::NewDepositAddress` and decides what to pay.
396//!
397//! There was briefly a `min_deposit` here, and a per-SSA `expected_deposit` on the commitment event to
398//! go with it. Both are gone. The Session layer has no price for a byte to derive one from, and a
399//! configured floor would not be a backstop but a second authority behind the first: set above the
400//! pool's price it kills a cycle the pool has already been paid for, on `max_deposit_wait`, with
401//! nothing on either side able to break the tie.
402//!
403//! ## The one fault with no dial: unverifiable shares
404//!
405//! An `UnverifiableShares` report closes the Session immediately, and there is no configuration for
406//! it. This used to be a pair of tolerances, per-SSA and per-Session, both shipped at zero.
407//!
408//! Shares are not checked on arrival — the non-constant coefficient commitments that made per-share
409//! verification possible were dropped — so a report means a whole *polynomial's* share set failed to
410//! open its commitment. The reconstructor marks that part failed, releases its shares, and never
411//! clears the flag; the SSA is the sum of every polynomial's constant term, so from that moment the
412//! cycle cannot be reconstructed by any means and will never pay. A tolerance would therefore not buy
413//! recovery, only unpaid service — including in the case it looks written for, a false positive from
414//! a verification bug, where the part is just as permanently failed. Closing on the first report also
415//! caps the exposure at the `threshold` packets already served when the failure surfaces, rather than
416//! a multiple of it.
417//!
418//! What the tolerances bought instead was machinery: absolute cross-peer totals, per-SSA and
419//! per-Session running sums, and delta accounting against the maximum seen so far to keep concurrent
420//! ack batches from double-counting. None of it is observable at a limit of zero, since the first
421//! report ends the Session.
422//!
423//! ## Constraints between parameters
424//!
425//! [`validate_pix_supervision`] enforces, at config-load time and against the reconstructor config
426//! actually in use: `max_recovery_idle >= max_ack_await_time`; `tombstone_retention_window >=
427//! max_ack_await_time`; `max_recovery_idle < unused_verifier_lifetime`;
428//! `commitment_recommit_interval < max_ssa_delivery_time`; `ssas_per_request` in
429//! `1..=MAX_SSA_BATCH_SIZE`; both scaled deadlines under 24 h; non-zero durations; a share fraction in
430//! `0.0..=1.0`; and non-zero `max_served_without_progress`, `min_share_order_sample` and
431//! `max_failed_cycles`.
432//!
433//! For [`fill`](SupervisorConfig::fill) it enforces a non-zero `heartbeat` under the same 24 h cap, a
434//! finite `finish_fraction` in `(0, 1]`, a finite `loss_margin` in `[0, 1)`, a `max_rate` inside
435//! `1..=MAX_FILL_RATE`, and a non-zero `min_surb_reserve`. One further constraint cannot be decided
436//! here because it spans the quota: `validate_incoming_session_pix_config` requires `max_rate` to
437//! clear the rate a cycle of the *widest accepted quota* needs to finish inside
438//! `finish_fraction × max_recovery_time`, which is 128 packets/s at the shipped defaults.
439//!
440//! ### The surplus run, and why it no longer constrains anything
441//!
442//! Emission is round-robin over a window of up to `hopr_protocol_pix::SHARE_EMISSION_WINDOW` (256)
443//! polynomials advancing in lockstep. They reach `threshold` on the same pass and then take their
444//! surplus shares together, so every block ends with `surplus_shares × window` consecutive packets
445//! carrying no *useful* share — **4096 at the shipped dimensions**, against a
446//! `max_served_without_progress` of 2048.
447//!
448//! That used to be a live constraint on two parameters, and an unmeetable one: the ceiling and the
449//! idle timer both counted useful shares, so the run looked exactly like an Entry gone silent. The
450//! gate would park the writer partway through, a parked writer spends no SURBs, and the idle rule
451//! could not rescue it — its re-arm branch needs *no service consumed* since the last progress, and
452//! 2048 packets were. An honest Session closed with `RecoveryIdle` one emission block into a cycle.
453//!
454//! Both now read [`SsaRecoveryProgress::shares_seen`](hopr_protocol_pix::SsaRecoveryProgress::shares_seen),
455//! which counts every share the cycle accepts — surplus included, up to the negotiated budget per
456//! polynomial. Full cryptographic recovery no longer cuts that signal off: the reconstructor drops
457//! its heavy state but retains one shared per-polynomial remainder, and the supervisor keeps that
458//! recovered predecessor as the paid front until the tail is exhausted or successor progress proves
459//! the FIFO boundary. The run therefore resets the ceiling and refreshes the idle deadline exactly
460//! like the useful shares around it, even across recovery, so **neither parameter has to be sized
461//! against the dimensions any more.** What `max_served_without_progress` still bounds is genuine
462//! silence: packets served with no share of any kind coming back.
463//!
464//! The one dimension-dependent property that remains is not a supervisor parameter at all: a
465//! polynomial's whole emission, `threshold + surplus`, should fit one peer deferral bucket
466//! (`hopr_protocol_pix::MAX_DEFERRED_ACKS_PER_POLYNOMIAL`, 128), or acknowledgements arriving before
467//! the cycle's commitments install can be dropped. The shipped 96 fits; both halves are a byte wide
468//! on the wire, so the sum can reach 510. It is a sufficient condition rather than a required one —
469//! only the pre-install prefix is deferred — which is why it is asserted on the defaults rather than
470//! enforced.
471//!
472//! ## Worked example
473//!
474//! A profile of **5 Mbps sustained per direction** and **5–6 s on-chain settlement** for an SSA
475//! deposit. `HoprPacket::PAYLOAD_SIZE` is 1038 B, so 5 Mbps is ~602 packets/s of return traffic —
476//! one SURB and one share each.
477//!
478//! **Dimensions first**, because every supervisor value derives from them. `2048 × 64` with the
479//! derived surplus of 16 gives 131 072 useful shares out of 163 840 emitted, and a cycle of 163 840
480//! packets — about **4.5 min** at this rate. The quota is priced on all of them, surplus included, so
481//! it is `2048 × 80 × 1038 B` = **162.2 MiB**, which is exactly the bottom of the default
482//! `quota_range` (a quarter of the 648.8 MiB the default dimensions imply), so no range change is
483//! needed. The default `8192 × 64` would make that 18.1 min per cycle, which at 6 s settlement is a
484//! long time to leave one cycle's traffic unsettled for no benefit. Keep it a multiple of 256 so the
485//! emission window never narrows.

542/// Configuration for the `SessionPixSupervisor`.
543///
544/// Reachable from a node's configuration file as
545/// `incoming_session_pix_config.supervision`. The fields interact — with each other and with the
546/// reconstructor's own lifetimes — so a set of them is only meaningful as a whole; that is what
547/// [`validate_pix_supervision`] checks, and the node's config validator runs it at load time.
548///
549/// A worked set of values, and what each field defends against, is written out under
550/// "Configuration" in the `supervision` module documentation — the module is crate-private, so it is
551/// named rather than linked here.
552#[derive(Debug, Clone, PartialEq, smart_default::SmartDefault, serde::Serialize, serde::Deserialize)]
553#[serde(default, deny_unknown_fields)]
554pub struct SupervisorConfig {
555    /// Maximum number of SSAs the Exit may ask the Entry to commit to in one `SsaRequest`.
556    ///
557    /// With [`allow_dynamic_ssa_batches`](Self::allow_dynamic_ssa_batches), Session admission picks
558    /// the smallest batch no larger than this value whose total quota is inside the Exit's accepted
559    /// range. With dynamic batching disabled, this remains the exact batch size, preserving the
560    /// original fixed-batch behavior. Batching amortizes the request round trip over several deposit
561    /// cycles. It lives here rather than beside the other Exit settings because the supervisor acts
562    /// on the selected value: it allocates the indices and scales both deadlines below by this factor.
563    ///
564    /// Two things it costs, both linear in the value:
565    ///
566    /// * Up to two batches can own live reconstructor state — worst case ≈41 MiB per cycle at the profiled dimensions,
567    ///   per `hopr_protocol_pix::peak_cycle_bytes`. That cost is reserved up front against
568    ///   `IncomingSessionPixConfig::max_live_cycle_bytes`; the supervisor enforces the two-generation/full-cycle bound
569    ///   before allocating, so this value directly divides the number of PIX Sessions the node will admit.
570    /// * The unfunded exposure within one batch: every cycle is initially requested unfunded, so the commitment and
571    ///   deposit deadlines cover this many SSA quotas rather than one. The front-aware service gate still grants only
572    ///   the current cycle's bounded predeposit allowance.
573    ///
574    /// **Must not exceed the peer Entry's `max_ssas_per_request`.** The batch size is not negotiated
575    /// — `StartSession.additional_data` is fully allocated (PIX dimensions in the upper 32 bits, SURB
576    /// balancer target in the lower 32), so the Entry cannot advertise its cap and the Exit cannot
577    /// learn it. An Entry that finds a batch too large refuses it in full and replies with an
578    /// `UnacceptablePixParams` `SessionError`, which closes the Session on both sides in about a round
579    /// trip. Every such Session is still lost; the reply only makes the failure immediate and
580    /// attributable instead of surfacing as a commitment timeout.
581    ///
582    /// Range-checked by [`validate_pix_supervision`] and clamped where it is read, so it can never
583    /// exceed `MAX_SSA_BATCH_SIZE`.
584    ///
585    /// Default: 1, which reproduces the unbatched exchange byte-for-byte.
586    #[default(1)]
587    pub ssas_per_request: usize,
588
589    /// Whether Session admission may derive a smaller SSA batch from the Entry's offered quota.
590    ///
591    /// When enabled, the Exit tries batch sizes from one through
592    /// [`ssas_per_request`](Self::ssas_per_request) and selects the first whose total quota is inside
593    /// `IncomingSessionPixConfig::quota_range`. If none fits, the Session is refused with
594    /// `UnacceptablePixParams`. Choosing the smallest fit limits Entry work, deposits, Exit memory,
595    /// and the chance of exceeding the Entry's unadvertised `max_ssas_per_request` cap.
596    ///
597    /// When disabled, the offered per-SSA quota itself must be inside `quota_range`, and the Exit
598    /// requests exactly `ssas_per_request` SSAs, matching the behavior before dynamic batching.
599    ///
600    /// Default: `true`.
601    #[default(true)]
602    pub allow_dynamic_ssa_batches: bool,
603
604    /// Cycles this Session may lose without recovering them before it is closed. The next one closes
605    /// it.
606    ///
607    /// Counted over the whole Session, not per batch, because a retired cycle leaves no trace on its
608    /// siblings: without a cumulative count an Entry can lose one cycle per batch forever while a
609    /// single funded sibling keeps the Session alive, paying for a fraction of what it is served.
610    ///
611    /// Only reachable with [`ssas_per_request`](Self::ssas_per_request)` > 1`. At the shipping batch
612    /// of one the failing cycle is always the last one standing, and that closes the Session before
613    /// this is ever consulted — so nothing changes at the defaults.
614    ///
615    /// A recovered cycle never counts: it leaves through tombstone expiry, not through the failure
616    /// path.
617    ///
618    /// Default: 1 — one lost cycle is survivable, which is what the retire-and-hand-on-the-successor
619    /// -gate path exists for, and a second is not.
620    #[default(1)]
621    pub max_failed_cycles: usize,
622
623    /// Maximum time to wait for the SSA to be fully committed.
624    ///
625    /// Together with [`max_deposit_wait`](Self::max_deposit_wait) this bounds how long a Session may
626    /// be served unincentivized: the Entry has to be able to deliver its SSA commitment before it
627    /// can be asked to pay for it.
628    ///
629    /// Multiplied by [`ssas_per_request`](Self::ssas_per_request) when the deadline is armed: a batch
630    /// asks the Entry for that many commitment sets in answer to one request, and all of their clocks
631    /// start together, so holding each to a single cycle's budget would fail an Entry that is
632    /// answering in order.
633    ///
634    /// Default: 20 s.
635    #[default(Duration::from_secs(20))]
636    #[serde(with = "humantime_serde")]
637    pub max_ssa_delivery_time: Duration,
638
639    /// How long a *partially* delivered commitment may go quiet before the missing parts are
640    /// re-requested.
641    ///
642    /// The Entry's answer to an `SsaRequest` is not one message but hundreds of them, and the Exit
643    /// can use none of it until every one has landed — so a single lost packet used to cost the whole
644    /// Session on [`max_ssa_delivery_time`](Self::max_ssa_delivery_time), typically after the Entry
645    /// had already been told to fund the cycle's deposit address. This is the timer that repairs it:
646    /// on expiry the Exit asks the Entry to re-send the polynomial commitments it never received.
647    ///
648    /// An *idle* timer, armed and re-armed by each arriving commitment message, so it measures
649    /// silence rather than elapsed time and the first ask cannot land in the middle of the burst.
650    /// It is only ever armed once something has arrived: a commitment nothing was delivered for has
651    /// no scope to name, and there is nothing the Exit could ask for.
652    ///
653    /// It bounds nothing on its own — `max_ssa_delivery_time` remains the absolute deadline, so the
654    /// unincentivized exposure of a cycle is unchanged however often this fires. How many asks a
655    /// cycle makes is bounded by count rather than by this interval:
656    /// [`MAX_COMMITMENT_RETRANSMISSIONS`](hopr_protocol_pix::MAX_COMMITMENT_RETRANSMISSIONS), which
657    /// is also exactly how many the Entry will answer, so shortening this buys promptness and never
658    /// a flood of wasted packets.
659    ///
660    /// Default: 3 s — well clear of the time a full burst takes to arrive, and short enough that a
661    /// repair completes several times over inside the delivery deadline.
662    #[default(Duration::from_secs(3))]
663    #[serde(with = "humantime_serde")]
664    pub commitment_recommit_interval: Duration,
665
666    /// Maximum time to wait for a deposit after the commitment is verifiable.
667    ///
668    /// Also multiplied by [`ssas_per_request`](Self::ssas_per_request). Each cycle's clock starts at
669    /// its own commitment, which staggers them somewhat — but a batch's commitments arrive
670    /// back-to-back while an Entry funding them serially finishes the last one that many deposits
671    /// later, so the stagger does not cover it.
672    ///
673    /// Default: 60 s.
674    #[default(Duration::from_secs(60))]
675    #[serde(with = "humantime_serde")]
676    pub max_deposit_wait: Duration,
677
678    /// Maximum idle time during recovery when service is being consumed.
679    ///
680    /// Gated on service consumption — if no packets were served, the timer
681    /// re-arms instead of closing.
682    ///
683    /// Default: 60 s.
684    #[default(Duration::from_secs(60))]
685    #[serde(with = "humantime_serde")]
686    pub max_recovery_idle: Duration,
687
688    /// Absolute per-SSA recovery deadline (immutable once set).
689    ///
690    /// This is a **resource backstop** (session slot + reconstructor memory),
691    /// not the anti-drip mechanism. The service-gated idle rule is.
692    ///
693    /// ## Why two hours, and not one
694    ///
695    /// It has to cover the *whole* of a cycle at the dimensions the node will accept, and at the
696    /// default dimensions one cycle does not fit in an hour. Emission runs in lockstep over windows
697    /// of [`SHARE_EMISSION_WINDOW`](hopr_protocol_pix::SHARE_EMISSION_WINDOW) polynomials, so with
698    /// 8192 polynomials the last useful share of the cycle lands at
699    ///
700    /// ```text
701    /// (31 full windows x 80 emitted + 1 window x 64 useful) x 256 = 651 264 packets
702    /// ```
703    ///
704    /// which is just over **60 minutes** at the 1.5 Mbps per-Session cap this crate documents, before
705    /// any mixing latency or loss. A one-hour ceiling closes an honest, fully saturated Session at
706    /// the default configuration with its last useful share only about 18 seconds away — and the
707    /// partial cycle is worth nothing, since the SSA is the sum of every polynomial's constant term.
708    ///
709    /// This is deliberately not the same count as the 655 360 quoted in the module documentation's
710    /// parameter table, and the two must not be reconciled: 655 360 is `8192 × 80`, the *full*
711    /// emission including the last window's surplus, which is what `quota_range` prices and what
712    /// `validate_incoming_session_pix_config` checks this value against. 651 264 is where the last
713    /// *useful* share lands, which is the point this argument is about — a deadline that clears the
714    /// useful shares but not the surplus tail still collects a payable cycle.
715    ///
716    /// Two hours is the value the worked profile in the module documentation already used, and it
717    /// keeps this instrument where it belongs: far enough out that
718    /// [`max_recovery_idle`](Self::max_recovery_idle) is what actually binds.
719    ///
720    /// The clock starts when the cycle reaches the paid transport front. That is deliberately later
721    /// than merely becoming the earliest unrecovered record: the predecessor's buffered surplus tail
722    /// can still occupy ~4096 packets, ~23 s at that rate, and remains bounded by the predecessor's
723    /// original hard clock. Starting the successor at the FIFO boundary prevents that pipeline delay
724    /// from being charged twice. A funded cycle that reaches the front and is never served is still
725    /// caught.
726    ///
727    /// `HoprProtocolConfig::validate` checks this against the dimensions the node will actually
728    /// accept, so a raised `quota_range` that outgrows it is refused at load rather than discovered
729    /// one closed Session at a time.
730    ///
731    /// Default: 2 hours.
732    #[default(Duration::from_secs(7200))]
733    #[serde(with = "humantime_serde")]
734    pub max_recovery_time: Duration,
735
736    /// Largest share of recovery progress that may land on a cycle *other* than the one at the front
737    /// of the batch, as a fraction of all progress since that cycle took the front.
738    ///
739    /// ## What it defends
740    ///
741    /// A batch only de-risks the Exit if its cycles are served one at a time, so that recovering the
742    /// first pays for the traffic that earned it. An Entry that instead spread a batch's shares across
743    /// all `ssas_per_request` cycles could take `ssas_per_request × quota` of service while leaving
744    /// every cycle short of recovery — and a cycle short of recovery pays nothing at all, since the SSA
745    /// is the sum of *every* polynomial's constant term. That turns the batch knob from cost-neutral
746    /// into an n-fold amplifier of unpaid traffic.
747    ///
748    /// Nothing else sees it. The service gate and [`max_recovery_idle`](Self::max_recovery_idle) both
749    /// measure the *absence* of progress, and a spreading Entry makes progress on every cycle
750    /// continuously — including the front one, whose idle timer it therefore keeps refreshing. It
751    /// simply never finishes one.
752    ///
753    /// ## Why a fraction and not a count
754    ///
755    /// Out-of-order *arrival* is not an Entry property. SURBs cross the mixnet outbound and their
756    /// acknowledgements cross it again inbound, so arrival order is a permutation of emission order
757    /// whose width is roughly `delay_range × packet rate`. An absolute tolerance would therefore have
758    /// to be re-derived every time the mixer is reconfigured, and — being cumulative — would drift
759    /// into closing honest Sessions given enough cycle boundaries.
760    ///
761    /// A ratio has neither problem: a permutation of bounded width is a vanishing *fraction* of a
762    /// growing window, so widening `delay_range` cannot move it, and the denominator grows with the
763    /// numerator so nothing accumulates. It is also independent of packet **rate** (both terms scale
764    /// together, so unlike a wall-clock bound it implies no throughput floor), of **loss** (which hits
765    /// every cycle alike), and of **`surplus_shares`** — which matters even now that the surplus is
766    /// negotiated rather than Entry-private. The Exit knows the budget, not the spend: how many of a
767    /// cycle's emitted shares turn out to be useful depends on the loss the Entry actually met, so no
768    /// expected shares-per-packet ratio follows from the parameter. Comparing the batch's cycles
769    /// against each other cancels it.
770    ///
771    /// ## The value
772    ///
773    /// A conforming Entry sits at ~0: with emission clamped to one cycle
774    /// ([`hopr_protocol_pix::SHARE_EMISSION_WINDOW`]) the only off-front progress is boundary
775    /// reordering. Spreading across `n` cycles gives `(n − 1) / n` — 0.5 at two cycles, 0.67 at three.
776    /// 0.25 separates those with room on both sides.
777    ///
778    /// It bounds rather than eliminates: an Entry may divert up to this fraction and stay legal, so
779    /// worst-case unpaid exposure becomes ~`1 / (1 − f)` cycles instead of `n`. Alternating — serving
780    /// the front cycle honestly, then dumping on later ones — buys nothing, because the accounting only
781    /// resets when the front cycle *completes*, which means it was paid for.
782    ///
783    /// Default: 0.25.
784    #[default(0.25)]
785    pub max_off_front_share_fraction: f64,
786
787    /// Progress that must accumulate before
788    /// [`max_off_front_share_fraction`](Self::max_off_front_share_fraction) is judged at all, in useful
789    /// shares.
790    ///
791    /// A sample-size floor, not a tolerance: it does not bound how much a cheat can extract — the
792    /// fraction does that — it only refuses to convict on thin evidence.
793    ///
794    /// Sized by the one case that would otherwise produce a false positive: a cycle made
795    /// *unrecoverable* by loss. A polynomial that loses more than `surplus_shares` of its shares can
796    /// never reach its threshold, so its cycle stops progressing while later ones continue, and the
797    /// off-front fraction climbs to 1.0. That cycle is not something to close a Session over — it stops
798    /// progressing, its service-gated [`max_recovery_idle`](Self::max_recovery_idle) deadline expires,
799    /// it is retired, and the accounting resets on the new front. The sample floor only has to outlast
800    /// that window: ~181 shares/s at the deployed 1.5 Mbps cap over 60 s is ~10 900, so 16 384 leaves
801    /// ~1.5x headroom.
802    ///
803    /// Unlike an absolute tolerance this does not have to grow with Session length or track the mixer
804    /// configuration — it is a floor on evidence, evaluated once and then continuously.
805    ///
806    /// Very large values can make this rule effectively inert for a Session. To disable share-order
807    /// enforcement intentionally, prefer
808    /// [`max_off_front_share_fraction = 1.0`](Self::max_off_front_share_fraction). No fixed upper bound
809    /// is enforced because the accounting window can span multiple successor batches before the front
810    /// advances.
811    ///
812    /// Default: 16384 shares.
813    #[default(16384)]
814    pub min_share_order_sample: u64,
815
816    /// Cap on the provisional predeposit service budget.
817    ///
818    /// This buys the application an exchange while the current front cycle's deposit confirms on
819    /// chain; it is not needed for the Session to become fundable, so it is a
820    /// latency-versus-exposure dial rather than a correctness requirement. The initial front starts
821    /// with this allowance, and it is restored for an unfunded successor after a paid front leaves
822    /// the front, whether by recovery or a tolerated failure. Retiring an unfunded front does not
823    /// grant it again.
824    ///
825    /// **Zero is supported and means strict prepay**: the Exit answers nothing until a sufficient
826    /// deposit is confirmed. Everything on the path to funding — the `SsaRequest`, the Entry's
827    /// commitment, the deposit itself, and the SURB keep-alive stream — bypasses the egress gate, so
828    /// a zero budget stalls the application without ever stalling the funding handshake. Deliberately
829    /// *not* rejected by [`validate_pix_supervision`] for that reason, unlike
830    /// [`max_served_without_progress`](Self::max_served_without_progress), where zero would wedge a
831    /// Session that has already paid.
832    ///
833    /// The effective budget is `min(target_useful_shares - 1, max_predeposit_packets)`, so this value
834    /// is the binding one at any realistic set of PIX dimensions.
835    ///
836    /// Default: 10000 packets.
837    #[default(10000)]
838    pub max_predeposit_packets: u64,
839
840    /// Maximum packets served without a single share coming back, before the gate blocks further
841    /// service as a defence-in-depth backstop.
842    ///
843    /// A ceiling enforced by `ServiceGate::acquire` while the current front is funded. A
844    /// [`crate::HoprSessionInPixEvent::RecoveryProgress`] snapshot resets it only for that funded
845    /// front. The sole recovered predecessor temporarily remains that paid front while its
846    /// per-polynomial negotiated remainder drains; progress on an unfunded, queued, older, or
847    /// over-budget cycle does not grant service.
848    ///
849    /// Those events now follow `shares_seen` rather than `useful_shares`, which is what makes a flat
850    /// 2048 safe at any dimensions. Keyed on useful shares, this had to exceed
851    /// `surplus x min(polys, SHARE_EMISSION_WINDOW)` — 4096 at the shipped dimensions, twice
852    /// this value — because a conforming Entry emits a whole window's surplus in one contiguous run
853    /// during which no share is useful. The gate parked the writer partway through, and a parked
854    /// writer spends no SURBs, so nothing could arrive to release it. See
855    /// [`SsaRecoveryProgress::shares_seen`](hopr_protocol_pix::SsaRecoveryProgress::shares_seen).
856    ///
857    /// What it bounds now is genuine silence, and that is rate-independent: it is a count of
858    /// *packets*, so unlike [`max_recovery_idle`](Self::max_recovery_idle) it implies no throughput
859    /// floor.
860    ///
861    /// Default: 2048 packets.
862    #[default(2048)]
863    pub max_served_without_progress: u64,
864
865    /// How long to retain recovered-SSA diagnostic records and observer ownership.
866    ///
867    /// Must be >= the reconstructor's `max_ack_await_time`. The compact paid-tail receipt is separate
868    /// and may outlive this record; expiring a tombstone therefore does not truncate a FIFO drain.
869    ///
870    /// Default: 30 s.
871    #[default(Duration::from_secs(30))]
872    #[serde(with = "humantime_serde")]
873    pub tombstone_retention_window: Duration,
874
875    /// How the Exit keeps a funded cycle on course for its own deadline when the application is
876    /// quiet.
877    ///
878    /// Every other field above is a rule for *stopping*. This one is the single rule for *going*, and
879    /// it exists because the deadlines cannot be met by an idle Session: a funded cycle only recovers
880    /// once its whole emission has ridden back to the Entry, so at production dimensions a Session
881    /// averaging under ~46 return packets/s over a cycle loses its deposit to
882    /// [`max_recovery_time`](Self::max_recovery_time) — which is every idle or light client.
883    ///
884    /// See [`PixFillConfig`] for what it costs and what it is bounded by.
885    #[serde(default)]
886    pub fill: PixFillConfig,

889/// How the Exit fills the return direction of a funded PIX cycle when the application will not.
890///
891/// # Why the Exit has to send anything at all
892///
893/// A PIX Exit is paid per *return* packet. Each Exit → Entry packet spends one SURB carrying one
894/// share, and a funded cycle only recovers — only unlocks the deposit it has already been paid — once
895/// `polys × (threshold + surplus)` of them have gone out. That figure is 327 680 at the shipped
896/// dimensions. Nothing in the protocol makes the *application* send them: an idle VPN client, a
897/// tunnel between keystrokes, or a client that simply reads more than it writes all leave the Exit
898/// holding a funded cycle that will never complete. `max_recovery_time` then closes it, and because
899/// the deposit address derives from client and server commitments together, the money is stranded
900/// rather than refunded.
901///
902/// So the Exit sends its own keep-alives — "fill" — at whatever rate the remaining emission needs to
903/// clear the deadline, minus whatever the application is already providing. The mechanism is
904/// deliberately the existing SURB-level keep-alive stream rather than a new message: every shipped
905/// Entry already parses it, already counts it as a consumed SURB (so its balancer refills), and
906/// already credits it as service against the successor gate.
907///
908/// # What it costs the client
909///
910/// One cycle's quota per deadline while idle, and nothing at all while the application is busier than
911/// the required rate — [`heartbeat`](Self::heartbeat) is what fill drops to when organic egress
912/// already covers the need. The client accepts this as the price of a Session that completes its
913/// cycles; it funds successors exactly as it would have.
914///
915/// # What bounds it
916///
917/// Four separate things, because a rule that *sends* is the one rule in this module that could be
918/// turned against the node running it:
919///
920/// * [`max_rate`](Self::max_rate) caps the instantaneous rate.
921/// * [`min_surb_reserve`](Self::min_surb_reserve) stops fill from spending the SURBs the Session needs for its own
922///   replies, as a ceiling on a reserve derived per Session from the Entry's announced buffer target.
923/// * The stall rule holds fill at the heartbeat once the target cycle stops making progress, so a doomed cycle or a
924///   share-less SURB supply cannot burn `max_rate × max_recovery_time` SURBs.
925/// * The existing deadlines and the service gate are unchanged, and remain the backstop for a client that stops
926///   supplying SURBs at all.
927#[derive(Debug, Clone, PartialEq, smart_default::SmartDefault, serde::Serialize, serde::Deserialize)]
928#[serde(default, deny_unknown_fields)]
929pub struct PixFillConfig {
930    /// Whether the Exit originates fill keep-alives at all.
931    ///
932    /// Disabling it restores the behaviour of an Exit that only ever answers: funded cycles then
933    /// complete if and only if the application returns enough traffic, and the ones that do not are
934    /// closed by `max_recovery_time` with their deposits stranded. That is a defensible choice only
935    /// for a deployment whose clients are known to saturate their Sessions.
936    ///
937    /// Default: `true`.
938    #[default(true)]
939    pub enabled: bool,
940
941    /// The floor fill rate: one packet per this period, sent even when nothing needs sending.
942    ///
943    /// Fill never drops to silence while a funded cycle is in flight, for two reasons that have
944    /// nothing to do with the deadline. The Entry's own idle eviction is refreshed by this traffic,
945    /// and a Session whose Exit has gone quiet is one whose SURB balancer has no level report to act
946    /// on. It is also what makes the ramp observable: a rate that is *only* ever the computed one
947    /// cannot be told apart from a planner that has stopped planning.
948    ///
949    /// Expressed as a period rather than a rate because it is far below one packet per second and
950    /// [`FillRate`] carries its own unit, so `1 / 60 s` is exact rather than a rounded fraction.
951    ///
952    /// Default: 60 s.
953    #[default(Duration::from_secs(60))]
954    #[serde(with = "humantime_serde")]
955    pub heartbeat: Duration,
956
957    /// Fraction of [`SupervisorConfig::max_recovery_time`] by which a cycle should be finished.
958    ///
959    /// The planner aims at `hard_deadline − (1 − finish_fraction) × max_recovery_time` rather than at
960    /// the deadline itself, so the last quarter of the budget is margin: for the loss the
961    /// [`loss_margin`](Self::loss_margin) does not cover, for a mixnet delay spike, and for the
962    /// round trip the successor's commitment and deposit still need after this cycle recovers. Aiming
963    /// at the deadline exactly would make every cycle a photo finish, and a cycle that misses is
964    /// worth nothing at all rather than nearly everything.
965    ///
966    /// Default: 0.75.
967    #[default(0.75)]
968    pub finish_fraction: f64,
969
970    /// Fraction by which the remaining emission is inflated to cover return-path loss.
971    ///
972    /// Fill counts packets it *sends*; the cycle advances on shares that *arrive*. The difference is
973    /// return-path loss, which the Exit cannot observe directly — it sees the reconstructor's progress
974    /// and nothing about the packets that produced none. Rather than infer a loss rate from a signal
975    /// that also moves for a dozen other reasons, the planner simply sends this much extra and lets
976    /// the ordinary re-planning each second absorb whatever the real figure turns out to be.
977    ///
978    /// Default: 0.05.
979    #[default(0.05)]
980    pub loss_margin: f64,
981
982    /// Ceiling on the fill rate, in packets per second.
983    ///
984    /// This is the value that decides how much bandwidth an idle Session may cost, and it has to
985    /// clear the floor a cycle actually needs: the largest quota this node accepts, spread over
986    /// `finish_fraction × max_recovery_time`. `validate_incoming_session_pix_config` enforces exactly
987    /// that, so a cap set below it is refused at load rather than discovered one stranded deposit at a
988    /// time.
989    ///
990    /// Default: 250 packets/s, which is ~2 Mbps at `HoprPacket::PAYLOAD_SIZE` and about twice the
991    /// 128 packets/s the shipped defaults require.
992    #[default(250)]
993    pub max_rate: u32,
994
995    /// Ceiling on the SURBs that must remain estimated-available before a fill packet is emitted.
996    ///
997    /// Fill is the one egress on the Exit that has no application waiting on it, so it is the one
998    /// that must yield. Spending the last SURBs on fill is not merely wasteful: a return packet with
999    /// no SURB to ride holds *every* packet this node originates for the resolver's
1000    /// `surb_resolution_wait`, so an over-eager filler stalls the Session it is trying to save. The
1001    /// SURB-level notification is exempt — it is the signal that asks for more SURBs — but the
1002    /// heartbeat is not, being fill at its floor rather than a different message.
1003    ///
1004    /// A ceiling rather than the figure used, because the two sides of the comparison are chosen by
1005    /// different nodes: the reserve is measured against the Exit's estimate of its own SURB buffer for
1006    /// the Session, and how deep that buffer is is the *Entry's* decision, announced with its
1007    /// initiation. The effective reserve is therefore never more than a quarter of the Entry's
1008    /// announced buffer target, floored at one. Without that, an operator sizing this against a
1009    /// production buffer would also be deciding — unintentionally — that every Session whose Entry
1010    /// asks for a shallower one can never be filled at all: the estimate never reaches the reserve,
1011    /// every fill packet is withheld, and the funded cycle strands on
1012    /// [`max_recovery_time`](SupervisorConfig::max_recovery_time).
1013    ///
1014    /// Default: 500, matching `SurbStoreConfig::distress_threshold`. Against the 7 000-SURB balancer
1015    /// target of the worked profile a quarter is 1 750, so the configured value is what binds there
1016    /// and the derivation only engages on a Session whose Entry asked for less than four times it.
1017    #[default(500)]
1018    pub min_surb_reserve: u64,
1019}

1021/// A rate at which the Exit originates PIX fill keep-alives.
1022///
1023/// A count over a period rather than a float, because it maps one-to-one onto
1024/// `RateController::set_rate_per_unit` and therefore says exactly what the stream will do. The
1025/// heartbeat is one packet per minute; expressing that as `0.0166… packets/s` and converting back
1026/// would be a rounding error in a value whose whole purpose is to be small and exact.
1027#[derive(Debug, Clone, Copy, PartialEq, Eq)]
1028pub struct FillRate {
1029    /// Packets to emit per [`per`](Self::per).
1030    pub packets: u32,
1031    /// The period [`packets`](Self::packets) is measured over. Never zero.
1032    pub per: Duration,
1033}
1034
1035impl FillRate {
1036    /// Emit nothing. The rate a Session is left at once it has no funded cycle to fill for.
1037    pub const ZERO: Self = Self {
1038        packets: 0,
1039        per: Duration::from_secs(1),
1040    };
1041
1042    /// `packets` per second.
1043    pub const fn per_second(packets: u32) -> Self {
1044        Self {
1045            packets,
1046            per: Duration::from_secs(1),
1047        }
1048    }
1049
1050    /// One packet per `period` — the heartbeat form.
1051    pub const fn once_per(period: Duration) -> Self {
1052        Self {
1053            packets: 1,
1054            per: period,
1055        }
1056    }
1057
1058    /// Whether this rate emits nothing.
1059    pub const fn is_zero(&self) -> bool {
1060        self.packets == 0
1061    }
1062
1063    /// This rate in packets per second.
1064    ///
1065    /// Zero for a zero period as well as for zero packets: a period that cannot be divided by is not
1066    /// an infinite rate, it is a rate this planner refuses to have produced. Both routes by which a
1067    /// heartbeat reaches the planner guard against one — `validate_pix_supervision` rejects a zero for
1068    /// a config that was validated, and `SessionManager::new` raises it to a positive floor for the
1069    /// programmatic ones that never are — so this arm is a last line rather than the thing doing the
1070    /// work.
1071    pub fn as_packets_per_sec(&self) -> f64 {
1072        let per = self.per.as_secs_f64();
1073        if self.packets == 0 || per <= 0.0 {
1074            0.0
1075        } else {
1076            self.packets as f64 / per
1077        }
1078    }
1079}

1266///
1267/// Extracted from [`validate_pix_supervision`] because it is not the first validator to see them.
1268/// `validate_incoming_session_pix_config` derives the fill floor a cycle of the widest accepted
1269/// quota needs, and `SessionManager::start` calls it *before* `validate_pix_supervision` — as does
1270/// `HoprProtocolConfig`, where one is a field validator and the other a schema-level one. That
1271/// derivation runs `Duration::mul_f64(finish_fraction)`, which panics on a `NaN`, a negative, or a
1272/// product the monotonic clock cannot represent. A single `finish_fraction: .nan` in a YAML file
1273/// would therefore abort the node at load instead of being reported as the configuration error it
1274/// is; values above one, or a negative `loss_margin`, would quietly compute a floor lower than the
1275/// one the cycle needs. Both callers run this first so neither outcome is reachable.
1276///
1277/// Finiteness is tested before every range, and the ranges are two-sided, for the reason spelled out
1278/// on `max_off_front_share_fraction`: every IEEE comparison against `NaN` is false, so a one-sided
1279/// test admits it — and a `NaN` here is not inert. It propagates through the aim point into the
1280/// required rate, and a `NaN` rate compares false against every hysteresis threshold, so the planner
1281/// would hold whatever it last emitted for the life of the Session.
1282pub(crate) fn validate_fill_fractions(fill: &PixFillConfig) -> Result<(), TransportSessionError> {
1283    // Zero is excluded at the low end because it puts the aim point at the instant the cycle's clock
1284    // started — the planner would demand a whole cycle's emission within one sampling interval and
1285    // clamp to `max_rate` forever. One is included: aiming exactly at the hard deadline is a
1286    // defensible, if tight, choice.
1287    if !fill.finish_fraction.is_finite() || !(0.0 < fill.finish_fraction && fill.finish_fraction <= 1.0) {
1288        return Err(TransportSessionError::InvalidConfig(format!(
1289            "fill.finish_fraction ({}) must be a finite fraction in (0.0, 1.0]",
1290            fill.finish_fraction
1291        )));
1292    }
1293    // One is excluded at the top: a margin of 100 % doubles every cycle's emission budget, which is
1294    // not loss tolerance but a second cycle's worth of traffic. Zero is allowed and means "assume a
1295    // lossless return path", which is wrong but bounded — the per-second re-plan catches up.
1296    if !fill.loss_margin.is_finite() || !(0.0..1.0).contains(&fill.loss_margin) {
1297        return Err(TransportSessionError::InvalidConfig(format!(
1298            "fill.loss_margin ({}) must be a finite fraction in [0.0, 1.0)",
1299            fill.loss_margin
1300        )));
1301    }
1302    Ok(())
1303}

1305/// Validates that [`SupervisorConfig`] and [`SsaReconstructorConfig`] are
1306/// mutually consistent.
1307///
1308/// Returns an error if constraints are violated.
1309pub fn validate_pix_supervision(
1310    cfg: &SupervisorConfig,
1311    reconstructor_cfg: &SsaReconstructorConfig,
1312) -> Result<(), TransportSessionError> {
1313    if !(1..=crate::MAX_SSA_BATCH_SIZE).contains(&cfg.ssas_per_request) {
1314        return Err(TransportSessionError::InvalidConfig(format!(
1315            "ssas_per_request ({}) must be between 1 and {}",
1316            cfg.ssas_per_request,
1317            crate::MAX_SSA_BATCH_SIZE
1318        )));
1319    }
1320    // Zero would close the Session on the first lost cycle *and* on the last one standing, which is
1321    // the same thing at the shipping batch size but silently disables batching above it. The
1322    // supervisor clamps to one where it reads this; rejecting here is what an operator sees.
1323    if cfg.max_failed_cycles == 0 {
1324        return Err(TransportSessionError::InvalidConfig(
1325            "max_failed_cycles must be non-zero".into(),
1326        ));
1327    }
1328    if cfg.max_ssa_delivery_time.is_zero() {
1329        return Err(TransportSessionError::InvalidConfig(
1330            "max_ssa_delivery_time must be non-zero".into(),
1331        ));
1332    }
1333    // Both halves are dead config rather than merely odd. A zero interval fires the re-request timer
1334    // on the same instant it is armed, so every arriving commitment message answers itself with an
1335    // ask; an interval at or above the delivery deadline never fires before the deadline closes the
1336    // Session, which is exactly the failure the timer exists to prevent — and neither is visible to
1337    // the operator anywhere but here.
1338    if cfg.commitment_recommit_interval.is_zero() {
1339        return Err(TransportSessionError::InvalidConfig(
1340            "commitment_recommit_interval must be non-zero".into(),
1341        ));
1342    }
1343    if cfg.commitment_recommit_interval >= cfg.max_ssa_delivery_time {
1344        return Err(TransportSessionError::InvalidConfig(format!(
1345            "commitment_recommit_interval ({:?}) must be shorter than max_ssa_delivery_time ({:?}), or a partially \
1346             delivered commitment is never re-requested before the Session closes",
1347            cfg.commitment_recommit_interval, cfg.max_ssa_delivery_time
1348        )));
1349    }
1350    if cfg.max_deposit_wait.is_zero() {
1351        return Err(TransportSessionError::InvalidConfig(
1352            "max_deposit_wait must be non-zero".into(),
1353        ));
1354    }
1355    if cfg.max_recovery_idle.is_zero() {
1356        return Err(TransportSessionError::InvalidConfig(
1357            "max_recovery_idle must be non-zero".into(),
1358        ));
1359    }
1360    if cfg.max_recovery_time.is_zero() {
1361        return Err(TransportSessionError::InvalidConfig(
1362            "max_recovery_time must be non-zero".into(),
1363        ));
1364    }
1365    if cfg.tombstone_retention_window.is_zero() {
1366        return Err(TransportSessionError::InvalidConfig(
1367            "tombstone_retention_window must be non-zero".into(),
1368        ));
1369    }
1370    if cfg.max_served_without_progress == 0 {
1371        return Err(TransportSessionError::InvalidConfig(
1372            "max_served_without_progress must be non-zero".into(),
1373        ));
1374    }
1375    // A fraction outside 0..=1 is unreachable rather than strict — the ratio can never exceed 1 — so a
1376    // typo would silently disable the check instead of tightening it.
1377    if !cfg.max_off_front_share_fraction.is_finite() || !(0.0..=1.0).contains(&cfg.max_off_front_share_fraction) {
1378        return Err(TransportSessionError::InvalidConfig(format!(
1379            "max_off_front_share_fraction ({}) must be a fraction between 0.0 and 1.0",
1380            cfg.max_off_front_share_fraction
1381        )));
1382    }
1383    // Zero would judge the very first off-front share, which mixnet reordering alone can produce.
1384    if cfg.min_share_order_sample == 0 {
1385        return Err(TransportSessionError::InvalidConfig(
1386            "min_share_order_sample must be non-zero".into(),
1387        ));
1388    }
1389    // A zero period is not a fast heartbeat, it is a division by zero in `FillRate::as_packets_per_sec`
1390    // and an assertion inside `RateController::set_rate_per_unit`. Checked whether or not fill is
1391    // enabled, so that turning it on later cannot fail in a way that only shows up at run time.
1392    if cfg.fill.heartbeat.is_zero() {
1393        return Err(TransportSessionError::InvalidConfig(
1394            "fill.heartbeat must be non-zero".into(),
1395        ));
1396    }
1397    // Shared with `validate_incoming_session_pix_config`, which runs *earlier* and does arithmetic
1398    // with both of these — see the function's own documentation.
1399    validate_fill_fractions(&cfg.fill)?;
1400    // Zero would be a disabled filler that still claims to be enabled, which is the one state an
1401    // operator cannot diagnose from the metrics: the rate gauge would sit at the heartbeat and the
1402    // cycles would strand anyway. `enabled` is how fill is turned off.
1403    //
1404    // The upper bound is where `RateController` stops being able to represent the request: its
1405    // `MIN_DELAY` is 100 µs, so anything above 10 000 packets/s is silently clamped, and a silent
1406    // clamp on the one parameter that bounds egress is worse than a refusal. It is also ~83 Mbps of
1407    // keep-alives, which no Session should be asked to produce.
1408    if !(1..=MAX_FILL_RATE).contains(&cfg.fill.max_rate) {
1409        return Err(TransportSessionError::InvalidConfig(format!(
1410            "fill.max_rate ({}) must be between 1 and {MAX_FILL_RATE} packets/s",
1411            cfg.fill.max_rate
1412        )));
1413    }
1414    // Zero would let fill spend the Session's last SURB. That is not merely wasteful: a return packet
1415    // that finds no SURB blocks every packet this node originates for the resolver's
1416    // `surb_resolution_wait`, so the reserve is what keeps the filler from stalling the Session it is
1417    // filling for.
1418    if cfg.fill.min_surb_reserve == 0 {
1419        return Err(TransportSessionError::InvalidConfig(
1420            "fill.min_surb_reserve must be non-zero".into(),
1421        ));
1422    }
1423    if cfg.max_recovery_idle < reconstructor_cfg.max_ack_await_time {
1424        return Err(TransportSessionError::InvalidConfig(
1425            "max_recovery_idle must be >= max_ack_await_time".into(),
1426        ));
1427    }
1428    // An Exit below the floor asks for its next batch before any conforming Entry will admit the
1429    // request. The Entry's gate is computed at the floor precisely because this value does not travel
1430    // on the wire (see `MIN_EARLY_RECOVERY_THRESHOLD`), so the mismatch cannot be detected on the
1431    // link: the one-shot request is dropped, nothing acknowledges the refusal, and the Session dies
1432    // on `max_ssa_delivery_time` waiting for a commitment that was deliberately withheld. Rejecting
1433    // it here turns a silent remote failure into a local startup error, which is the only place the
1434    // operator who set the value can see it.
1435    //
1436    // Written as a range rather than `< floor`, and with the finiteness test in front, for the same
1437    // reason `max_off_front_share_fraction` above is: every IEEE comparison against `NaN` is false, so
1438    // `NaN < floor` admits it, and a `NaN` threshold is not inert — `ceil` leaves it `NaN` and casting
1439    // that to an integer saturates to zero, so the Exit signals early recovery on its first
1440    // reconstructed polynomial. That is the *earliest* possible request against a gate whose entire
1441    // job is to refuse early ones.
1442    if !reconstructor_cfg.early_recovery_threshold.is_finite()
1443        || !(hopr_protocol_pix::MIN_EARLY_RECOVERY_THRESHOLD..=1.0)
1444            .contains(&reconstructor_cfg.early_recovery_threshold)
1445    {
1446        return Err(TransportSessionError::InvalidConfig(format!(
1447            "early_recovery_threshold ({}) must be a finite fraction between MIN_EARLY_RECOVERY_THRESHOLD ({}) and \
1448             1.0; a lower value asks for the next SSA batch before a conforming Entry admits the request",
1449            reconstructor_cfg.early_recovery_threshold,
1450            hopr_protocol_pix::MIN_EARLY_RECOVERY_THRESHOLD
1451        )));
1452    }
1453    // Documented invariant: tombstone must outlive the ack window.
1454    if cfg.tombstone_retention_window < reconstructor_cfg.max_ack_await_time {
1455        return Err(TransportSessionError::InvalidConfig(
1456            "tombstone_retention_window must be >= max_ack_await_time (otherwise late acks arrive after the tombstone \
1457             expires)"
1458                .into(),
1459        ));
1460    }
1461    // The supervisor must give up on a stalled SSA before the reconstructor reclaims the state it
1462    // would need to finish one. Written against `unused_verifier_lifetime` because that is now the
1463    // only duration governing a live cycle: it is measured from the last acknowledged share
1464    // *anywhere* in the cycle, so a cycle that is still being served never expires and the two
1465    // deadlines only ever race on a cycle that has genuinely stopped.
1466    //
1467    // This replaces a comparison against `incomplete_ssa_lifetime`, which no longer exists. That
1468    // field was inert in any case — it was clamped to the larger of the two lifetimes, so the
1469    // default configuration always resolved it to 1800 s rather than its own 600 s — which is
1470    // exactly the kind of hand-held lifetime pairing that scoping reclamation to the cycle removed.
1471    if cfg.max_recovery_idle >= reconstructor_cfg.unused_verifier_lifetime {
1472        return Err(TransportSessionError::InvalidConfig(
1473            "max_recovery_idle must be < unused_verifier_lifetime".into(),
1474        ));
1475    }
1476    // Reject durations that would overflow the monotonic clock when used as
1477    // deadlines. See `MAX_SUPERVISOR_DURATION`.
1478    //
1479    // The first two are checked *as armed*, i.e. multiplied by the batch size, because that product
1480    // is the duration a deadline is actually set to. Checking the unscaled value would let a config
1481    // pass here and then be silently clamped at arming time, which is the failure mode this cap
1482    // exists to make loud.
1483    //
1484    // The other three are not scaled, so the scaling fact travels per entry rather than being
1485    // asserted for the whole loop. A blanket "as armed for a batch of N" invites the operator to
1486    // divide the reported figure by N and conclude they configured a value they did not — which is
1487    // the same class of misdirection the cap exists to prevent.
1488    for (name, dur, scaled) in [
1489        (
1490            "max_ssa_delivery_time",
1491            scaled_deadline(cfg.max_ssa_delivery_time, cfg.ssas_per_request),
1492            true,
1493        ),
1494        (
1495            "max_deposit_wait",
1496            scaled_deadline(cfg.max_deposit_wait, cfg.ssas_per_request),
1497            true,
1498        ),
1499        ("max_recovery_idle", cfg.max_recovery_idle, false),
1500        ("max_recovery_time", cfg.max_recovery_time, false),
1501        ("tombstone_retention_window", cfg.tombstone_retention_window, false),
1502        ("fill.heartbeat", cfg.fill.heartbeat, false),
1503    ] {
1504        if dur > MAX_SUPERVISOR_DURATION {
1505            let armed = if scaled {
1506                format!(", as armed for a batch of {}", cfg.ssas_per_request)
1507            } else {
1508                String::new()
1509            };
1510            return Err(TransportSessionError::InvalidConfig(format!(
1511                "{name} ({dur:?}{armed}) must not exceed {MAX_SUPERVISOR_DURATION:?}"
1512            )));
1513        }
1514    }
1515    // The two recovery clocks measure different things and only one of them is an anti-drip rule.
1516    // `max_recovery_idle` is service-gated, so it spares a Session that is merely quiet and closes
1517    // one that is consuming service while returning nothing. `max_recovery_time` is neither gated nor
1518    // refreshable — it is a resource backstop for the slot and the reconstructor state, and is
1519    // documented as such throughout this module.
1520    //
1521    // Set at or below the idle deadline, the backstop fires first on *every* cycle. The idle rule —
1522    // the only instrument that can tell a slow honest Session from a cheating one — becomes
1523    // unreachable, and honest Sessions are closed on `RecoveryDeadline` instead. Both values pass
1524    // every check above individually, so this inversion is invisible unless the two are compared.
1525    //
1526    // Checked after the cap loop deliberately. An over-cap `max_recovery_idle` cannot satisfy this
1527    // rule either — no legal `max_recovery_time` exceeds it — so running this first would make the
1528    // cap's own `max_recovery_idle` branch unreachable and swap a precise diagnostic for a vaguer
1529    // one. Representability first, then policy.
1530    if cfg.max_recovery_time <= cfg.max_recovery_idle {
1531        return Err(TransportSessionError::InvalidConfig(format!(
1532            "max_recovery_time ({:?}) must be > max_recovery_idle ({:?}); the hard deadline is a resource backstop, \
1533             and at or below the idle deadline it pre-empts the service-gated idle rule on every cycle",
1534            cfg.max_recovery_time, cfg.max_recovery_idle
1535        )));
1536    }
1537    Ok(())
1538}

1540/// Upper bound on any supervisor duration, as it is actually armed.
1541///
1542/// 24 h is far above anything a supervisor deadline should be, and the point is not the number but
1543/// the failure it forecloses: every phase reads an absent deadline as *no deadline*, and
1544/// `Instant::checked_add` returns `None` for a duration the monotonic clock cannot represent. So a
1545/// large enough configured value does not produce a long deadline, it produces none at all — the
1546/// supervisor silently stops enforcing that phase.
1547///
1548/// Enforced twice, and deliberately so. [`validate_pix_supervision`] *rejects* a config above it,
1549/// which is what an operator should see. `SessionManager::new` *clamps* to it, because nothing in
1550/// this crate calls `validate` and a programmatically assembled config would otherwise reach the
1551/// supervisor unchecked.
1552pub(crate) const MAX_SUPERVISOR_DURATION: Duration = Duration::from_secs(86400);
1553
1554/// Upper bound on [`PixFillConfig::max_rate`], in packets per second.
1555///
1556/// Set where `RateController` stops being able to honour the request rather than at a bandwidth an
1557/// operator would recognise: its `MIN_DELAY` of 100 µs makes 10 000 packets/s the fastest rate it can
1558/// express, and anything above it is clamped without a word. A cap that is *silently* not applied is
1559/// the failure this constant forecloses; that it is also ~83 Mbps of keep-alives is a second reason,
1560/// not the first one.
1561pub(crate) const MAX_FILL_RATE: u32 = 10_000;
1562
1563/// How often the fill planner re-derives the required rate.
1564///
1565/// One second is chosen against the two quantities it has to track. The required rate moves on the
1566/// scale of the recovery deadline (hours), so nothing is lost by sampling it slowly; the *organic*
1567/// rate moves on the scale of an application turning on, and a sampling interval far below the
1568/// [`ORGANIC_WINDOW`] would measure scheduler jitter rather than throughput. It is also the unit the
1569/// planner falls back to when the aim point is already in the past, which is why it must be a
1570/// duration a rate can meaningfully be quoted over.
1571pub(crate) const SAMPLING_INTERVAL: Duration = Duration::from_secs(1);
1572
1573/// Time constant of the exponential average the planner keeps of organic egress.
1574///
1575/// The point of the average is to answer "is the application already covering the need", and to
1576/// answer it without either chasing bursts or lagging a genuine start. Ten seconds is roughly the
1577/// duration over which a Session's throughput is a meaningful number at all — below it a TCP-shaped
1578/// workload is all bursts, above it the planner keeps filling for ten seconds after the application
1579/// has stopped, which is exactly the case fill exists to catch.
1580pub(crate) const ORGANIC_WINDOW: Duration = Duration::from_secs(10);
1581
1582/// A per-cycle deadline duration as it is actually armed for a batch of `ssas_per_request`.
1583///
1584/// One place computes this so the validator and the supervisor cannot disagree about what a
1585/// configuration means. `ssas_per_request` is clamped rather than trusted, because a supervisor can be
1586/// constructed from a config that never went through [`validate_pix_supervision`]; the multiplication
1587/// saturates for the same reason.
1588pub(crate) fn scaled_deadline(per_cycle: Duration, ssas_per_request: usize) -> Duration {
1589    per_cycle.saturating_mul(ssas_per_request.clamp(1, crate::MAX_SSA_BATCH_SIZE) as u32)
1590}
